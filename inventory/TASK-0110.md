# engine: the history map and UTC sub-second timestamps

The foundation every other lifecycle task builds on ([ADR-0099 — Lifecycle is config: transitions, history, derived blocked, priority](ADR-0099.md), decision 2). It
lands alone so the byte-identity pin changes once, deliberately.

Spec:

- Add `history` to the reserved keys (`frontmatter`, `store::decompose` /
  `reconstruct`, the closed-schema check). It is a map of RFC3339 UTC timestamp
  with sub-second precision (`2026-09-05T14:03:22.418Z`) to status. Keys are
  quoted; the serializer emits it one entry per line, sorted by key, reusing
  the relation-map formatter. Round-trip test: `reconstruct(decompose(doc))`
  byte-identical with a history map present.
- `commands::now_rfc3339` gains a UTC sub-second sibling for history keys;
  `created`/`updated` keep their current form. A key equal to the previous one
  (same instant) is bumped by one microsecond so two transitions never collide.
- Writers: `new` (first entry at the initial status), `set-status` (append),
  `import` (one entry at the given status). The store gets a
  `append_history(dkey, ts, status)` beside `touch`.
- Verify: last entry equals `status`; keys strictly increasing; `created`
  equals the first key when both exist; a document with no history is a
  problem named `missing history` so the migration document can grep for it.
- Update `opys/tests/cli.rs` expectations in one commit whose message says the
  pin moved because every `new` now writes history.
- Write `docs/migration-history.md`: for each document, seed `history` from
  `opys history --seed` ([TASK-0117 — engine: the gix branch reader, default-on, and the comrak trim](TASK-0117.md)) where git has the timeline, otherwise a
  single entry from `created` at the current status. Run it on this repo's own
  inventory as the last step of this task, with the `created` fallback.

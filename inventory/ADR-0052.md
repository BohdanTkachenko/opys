# The hosted plane is blind and unprivileged

## Context

The hosted service ([FEAT-0059 — Relay and Connect: remote access to your nodes](FEAT-0059.md)) sits between the user's clients (web, phone,
MCP) and the user's nodes (laptop, homelab, VPS). Whatever it *can* do defines
the blast radius of a compromise and the ceiling of user trust. Two separate
capabilities need bounding: what the cloud can **read** (registry content
passing through the relay) and what the cloud can **execute** (commands
delivered to hardware we do not manage). Retrofitting either bound after the
protocol exists is painful; both must be designed in from the first version.

## Decision

Two hard properties of the hosted plane:

1. **Blind**: node↔client traffic through the relay is end-to-end encrypted
   with keys the relay never holds; server-side state kept for continuity
   (e.g. the last-known snapshot shown while a laptop sleeps) is stored
   encrypted, decryptable only by the user's clients. The relay is identity,
   presence, and ciphertext routing — nothing else.
2. **Unprivileged**: the relay transports only the typed opys API (registry
   reads, command-core actions) to bring-your-own hardware. It never
   transports arbitrary command execution; shell access (browser terminal,
   SSH) exists only on managed VMs ([FEAT-0060 — Hosted environments: managed development VMs](FEAT-0060.md)), where the environment is ours
   to secure. A fully compromised relay account can, at worst, vandalize a
   task registry — never run code on a customer's machine.

Consented, feature-scoped exceptions to blindness (e.g. the hosted planning
assistant, [FEAT-0064 — Planning assistant: AI over the typed API](FEAT-0064.md), reading docs to plan) must be explicit, per-feature, and
avoidable (the same feature runs node-side with a user key).

## Consequences

- The typed API is also the support boundary: if a node speaks the API, the
  service works; everything behind it is the user's. This is what makes a
  cheap Connect tier supportable.
- Nodes broadcast registry state, not source code — the API scope structurally
  limits WIP exposure in team meshes; a per-node visibility toggle covers the
  rest.
- E2E key management (device enrollment, key rotation, recovery) becomes core
  protocol work in [FEAT-0059 — Relay and Connect: remote access to your nodes](FEAT-0059.md), not an afterthought.
- Marketing can make structural claims ("our cloud cannot read your registry
  or execute code on your machines") that competitors with server-side truth
  cannot.

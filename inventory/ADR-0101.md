# Verify observes time: stuck, visits, `--fix`, and exit code 3

## Context

Two things an agent loop has to notice are not content problems. A document can
sit in a status past any reasonable time for that project, which means the agent
that took it is gone, or is thinking about it for far too long; and a document
can bounce between two statuses forever, because the coder and the reviewer
disagree and neither is a person.

Neither is a snapshot invariant. A corpus is valid when written and *becomes*
stuck with no write at all. The existing machinery has no place for that. The
auto-sync pass runs inside every mutating command, so a clock-driven side effect
there would make a plain `tag` flip statuses and would break the byte-identity
tests. The node is a view ([ADR-0051 — Files and git are the only truth; the server is a view](ADR-0051.md)) with no writer of its own. And a hardcoded
threshold would be wrong for every project but one: a fast-paced repository
wants minutes, a "ship the game" feature might legitimately sit for two years.

[ADR-0099 — Lifecycle is config: transitions, history, derived blocked, priority](ADR-0099.md)'s history map supplies what is needed: the last key is when the
document entered its status, and the number of entries for a status is how
often it has been there.

## Decision

1. **Thresholds are per-type, per-status config**, never constants:
   `[types.X.ttl]` maps a status to a duration, and `[types.X.max_visits]` maps a
   status to `{ limit = N, then = "<status>" }`.

2. **Stuck and overflow are observations, not problems.** Verify reports them
   under their own heading. `next` ([FEAT-0106 — `opys next`: the pick oracle](FEAT-0106.md)) and the flow view ([FEAT-0109 — Flow graph view: statuses as nodes, agents as loops](FEAT-0109.md))
   compute them from the same engine predicate, one function, so the three
   never disagree about who is stuck. They never change the exit-code class of
   content problems.

3. **`verify --fix` applies the configured transitions**: a stuck document moves
   to its status's configured target, an overflowed one to its `then`. Each is a
   normal transition: history appended, the sync pass run, the layout
   relocation performed. The fixable list is closed, exactly those two.
   Everything sync repairs stays sync's, so there is one auto-fixer per trigger.

4. **Exit codes.** `0` clean and `1` content problems and `2` error are
   unchanged. `3` means every finding is fixable and nothing else was found.
   With `--fix`, the code reflects what remains after fixing. CI should gate on
   `1`; since most scripts gate on nonzero, the README says so.

5. **The clock is injectable.** `OPYS_NOW` (RFC3339) overrides the wall clock,
   so tests and CI reruns of one commit are deterministic.

6. **In server mode, every verification autofixes, on by default.** The node
   runs `--fix` semantics on each corpus it verifies, including agents'
   worktrees, on the premise that a fix is always safe. That premise is a design
   constraint on the fixable list, not a hope: a fixable transition must be safe
   to apply under a running agent, so the type's transitions must declare an
   edge from a stuck target back to the working status (an agent flipped to
   stuck resumes with one `set-status`), and a `then` target must be reachable
   back as well; `config validate` checks both. `autofix = false` in
   `server.toml` turns it off. Every autofix is the ordinary engine write cycle
   (its own `Project` and `Store`, the inventory flock, never a warm store) and
   is announced as an `action-completed` event like any other write.

## Consequences

- Verify becomes a mutating command in `--fix` mode and takes the inventory
  lock like every other one.
- The same commit can exit `0` today and `3` tomorrow. The separate code
  isolates that class; `OPYS_NOW` removes it from tests.
- The node gains its first self-initiated write. [ADR-0051 — Files and git are the only truth; the server is a view](ADR-0051.md)'s "never a second
  write authority" is preserved in mechanism (the same engine write cycle,
  nothing through a warm store) and narrowed in policy: the node now initiates
  writes of one closed class. [FEAT-0058 — opys-server: the always-on node](FEAT-0058.md)'s guardrails are amended to say so.
- With autofix on, the dashboard's verify dot mostly shows clean or problems;
  the third state exists for `autofix = false` and for the CLI.
- A TTL that is short for one task will flip it under a running agent. That is
  the accepted cost of "always safe", and the recovery edge is what makes it
  safe rather than merely survivable.

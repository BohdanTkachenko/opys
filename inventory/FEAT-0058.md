# opys-server: the always-on node

The node daemon: a long-lived process on the user's machine (laptop, homelab,
VPS) that watches configured project roots — discovering `opys.toml` projects
*and their git worktrees* — and holds a warm, watcher-refreshed store per
corpus ([ADR-0051 — Files and git are the only truth; the server is a view](ADR-0051.md): the existing load→SQL→flush lifecycle held open; reload on
debounced file events, ~100 ms per 1,400-doc corpus, a few MB memory each).
It serves the **typed opys API** over HTTP + WebSocket and an embedded
single-page web UI on localhost. Stage 1 of the platform; free tier 1 of
[ADR-0053 — Everything open source; sell connectivity, hosting, and convenience](ADR-0053.md) ("run opys on your laptop, get a localhost URL").

Surface (v1):

- **Reads**: projects/worktrees list, docs (list/filter), doc body (rendered),
  SELECT queries via the plan-guarded `run_user_query` ([FEAT-0010 — SQL query surface](FEAT-0010.md) is the API's
  query language — the board, filters, and stats are SELECTs).
- **Health**: `verify::collect_problems` per corpus, live — the dashboard's
  red/green per project/worktree is the headline widget ([FEAT-0009 — verify: the CI gate](FEAT-0009.md)).
- **Events**: WS push on corpus change, verify-status change, presence.
- **Actions**: the command cores (new/set-status/tag/block/unblock/close),
  executed locally against the files under the [FEAT-0021 — Parallel-agent write safety](FEAT-0021.md) advisory lock —
  remote hands on the same local write path; never a second write authority.
- **Worktree union view**: one merged, *labeled* view across a project's
  worktrees (main + per-worktree overlays). This is deliberately the same
  machinery a team's branch/node overlays will use later ([FEAT-0063 — Teams: node mesh, union view, per-seat plan](FEAT-0063.md)) — build
  it corpus-plural from day one.

Non-goals: no arbitrary command execution in the API ([ADR-0052 — The hosted plane is blind and unprivileged](ADR-0052.md) — shell is not
a thing this API can express); no persistence beyond the files (restart =
rescan); no auth in local mode (bind localhost/tailnet); no stats endpoint
(the query surface covers it).

## Plan

The build is [TASK-0067 — opys-server: scaffold the AGPL crate](TASK-0067.md) … [TASK-0075 — opys-server: systemd install, docs, and M1 closeout](TASK-0075.md), chained with `blocked_by` in dependency
order — **a task is pickable iff its status is `todo`** (blocked ones become
pickable as their blockers close). [TASK-0067 — opys-server: scaffold the AGPL crate](TASK-0067.md) and [TASK-0068 — engine: extract print-free cores for block/unblock](TASK-0068.md) are independent
starting points. Every task body is a self-contained spec: the architectural
decisions are already made there; implement them as written, and when a spec
turns out to be impossible or wrong, stop and record the problem in the task's
Progress log instead of improvising a different design.

Pickup protocol per task:

1. `opys set-status TASK-00NN in-progress`.
2. Implement exactly the task's spec; keep every commit green against the full
   CI gate (`cargo fmt --all --check`, both clippy passes with `-D warnings`,
   `cargo test --all --all-features`, `msrv`).
3. Check the task's checklist items, append a Progress line summarizing what
   landed, run `opys verify`, commit (Conventional Commits), push to main.
4. `opys close TASK-00NN`.
5. For each task the closed one was blocking: `opys unblock <id> --by
   TASK-00NN` — it reverts to `todo` and becomes pickable.

## Implementation guardrails (read first, apply to every task)

- **The warm store is a read-only cache.** Release the inventory lock
  immediately after every load (`drop(store.take_lock())`) — a warm store
  holding the lock deadlocks every CLI invocation. Never flush a warm store.
- **Writes are fresh CLI-identical cycles**: `Project::open` → `backend.load`
  (lock) → engine `core()` → sync pass → `backend.flush`. The server contains
  no write logic of its own — if a write behavior isn't reachable through an
  engine core, extend the engine (print-free, CLI behavior pinned by the
  existing tests), don't reimplement it server-side.
- **License boundary** ([ADR-0056 — License split: Apache-2.0 core, AGPL server components](ADR-0056.md)): `opys-server` is AGPL-3.0-only;
  `opys-engine`, the backend, and the `opys` binary stay Apache-2.0 and must
  never depend on the server crate.
- **No shell, ever** ([ADR-0052 — The hosted plane is blind and unprivileged](ADR-0052.md)): the API's action surface is a closed,
  serde-validated enum; no endpoint accepts commands or filesystem paths.
- **Engine changes must keep the CLI byte-identical** — the integration suite
  in `opys/tests/cli.rs` is the behavioral pin; if a test needs editing to
  pass, the change is wrong.
- **MSRV 1.88 stands**: verify with the `msrv` devShell command after any
  dependency change; pin older dep versions rather than raising the floor.
- **Dogfood**: this repo's own inventory is the first fixture — the server
  must run cleanly over `inventory/` throughout.

## Decisions (formerly open questions)

- **Web UI stack**: no build pipeline — vanilla ES modules + one stylesheet
  embedded via `include_str!`, zero external requests ([TASK-0074 — opys-server: embedded web UI](TASK-0074.md)).
- **Watcher**: `notify` recommended-watcher per corpus base + the project's
  `opys.toml`, 250 ms debounce, plus a 60 s discovery rescan for corpus
  add/remove ([TASK-0070 — opys-server: corpus actor with warm store and watcher](TASK-0070.md)). The retired TUI's watcher is prior art only; the
  code is written fresh in the server crate.
- **Process shape**: separate `opys-server` binary (the Apache CLI is
  untouched); default bind `127.0.0.1:6797`; one actor thread per corpus,
  store created inside the thread.
- **Publishing**: `publish = false` until the M2 milestone.

## Test plan
- [ ] discovery finds nested projects and their worktrees; corpora stay isolated per worktree
- [ ] a file edit is reflected in API reads and pushed over WS within the debounce window
- [ ] verify status per corpus updates live and matches `opys verify` exit semantics
- [ ] API actions go through command cores + lock and are rejected exactly when the CLI would reject them
- [ ] the API cannot be made to execute arbitrary commands (no such endpoint; unknown actions are 400s)
- [ ] server survives a corpus that fails to parse (serves the parse errors, keeps other projects live)
- [ ] a warm server never blocks a concurrent CLI invocation (the lock-release regression test)

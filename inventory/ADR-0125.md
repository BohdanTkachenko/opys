# Comment threads live in the document they discuss

## Context

The loop opys serves is a human reviewing what agents wrote and an agent acting
on what the human said. Today the only way to say "this paragraph is wrong" from
the dashboard is to edit the body, which loses the distinction between the
document and the conversation about it, or to say it in a chat the next agent
will never see. Reviewers want what Google Docs and GitHub reviews give them: a
thread anchored to a passage, replies, and a resolved state. Agents need the
same threads as a queue they can poll (what is waiting on me?) and a way to
answer and open threads themselves, from the CLI.

Where the threads are stored decides everything else. Candidates:

1. A sidecar file per document (`FEAT-0001.comments.md` or a `_comments/` dir).
2. A server-side store owned by the node.
3. Frontmatter (a `comments` map).
4. The document itself: anchors in the body, threads in a reserved section.

How a thread is anchored is the second question. A quote-only anchor (find the
passage by its text) survives in no file at all and goes stale silently when
the text is edited; an in-text marker is exact and moves with the text, at the
price of syntax in the body that every writer has to preserve.

## Decision

1. **Threads are part of the document** ([ADR-0051 — Files and git are the only truth; the server is a view](ADR-0051.md)): a thread
   travels with its branch, merges with git, shows in a diff, greps with `rg`,
   and needs no node to exist. A server store (2) would make the node a source
   of truth; a sidecar (1) doubles every relocation, retire and close;
   frontmatter (3) is closed and canonical, and multi-paragraph prose in YAML
   reads badly.

2. **An open thread is anchored by a marker pair in the body**, HTML comments
   so every markdown renderer hides them:

   ```markdown
   <!--comment id="C1"-->the anchored text<!--/comment id="C1"-->
   ```

   Pairs match by id, so ranges may nest or overlap. A pair stays inside one
   `##` section, may span lines, and may not open or close inside a code span
   or fence (there a comment is literal text; the CLI anchors around the whole
   fence instead). A thread with no marker pair is document-level.

3. **The threads live in a reserved trailing `## Comments` section**, one `###`
   block per thread: id and state in the heading, the anchored text as it was
   when the thread opened in a blockquote, then one list item per entry:

   ```markdown
   ## Comments

   ### C1 · open

   > **Test plan** — the anchored text

   - **Bohdan Tkachenko** · human · 2026-10-09T10:42:07Z

     The entry's markdown, any number of paragraphs.
   ```

   Ids are per document (`C1`, `C2`, …), drawn one past the highest ever used
   in it, and never reused. State is `open` or `resolved`. An entry carries an
   author, an author kind (`human` or `agent`) and a UTC timestamp.

4. **Resolving removes the markers; the blockquote keeps the record.** A
   resolved thread no longer marks up the text it was about. `reopen` puts the
   markers back if the recorded text is still found exactly once in its
   section, and otherwise reopens the thread as document-level and says so.

5. **The format is enforced, not advisory.** It is a code-backed section kind
   with its own parser, and `verify` fails on: an open thread whose markers are
   missing, unpaired, duplicated, crossing a section boundary, inside code, or
   wrapping empty text; markers whose id has no thread; markers left on a
   resolved thread; a duplicate or reused id; an unknown state; an entry that
   does not parse; a `## Comments` section on a type that does not enable it.
   Every write goes through `opys comment …` (and the node's typed actions,
   which call the same code), so a hand edit that breaks a marker is caught
   by the CI gate rather than silently losing the anchor.

6. **Whose turn it is is derived, not stored**: an open thread whose last
   entry is by a human is the agent's turn, and vice versa. That is what
   `--turn=agent` filters on, and it cannot drift from the entries.

7. **Comments are invisible to everything else.** Markers are stripped and
   the `## Comments` section is skipped by title and section extraction, the
   `sections`/`blocks` projections, section checks and mdprism validation, so
   `opys query` over body text and the existing checks see the document as if
   it had no comments. Linkify still runs inside entry text.

8. **Comments are opt-in per type** (`comments = true`). `close` deletes an
   ephemeral document and its threads with it, so `close` names any open
   threads before it runs.

### A document with two threads

```markdown
## Test plan

- [ ] <!--comment id="C1"-->a revision is attributed to the commit that introduced it<!--/comment id="C1"-->
- [ ] `opys diff <id>` with no revisions diffs the last commit against the working copy

## Comments

### C1 · open

> **Test plan** — a revision is attributed to the commit that introduced it

- **Bohdan Tkachenko** · human · 2026-10-09T10:42:07Z

  Isn't this already fixed? history.rs says so in its module doc.

### C2 · resolved

> **Behaviour** — Revisions on other branches stay the union view's job

- **Bohdan Tkachenko** · human · 2026-10-09T10:44:51Z

  Should this include commits on other branches?

- **claude** · agent · 2026-10-09T11:03:12Z

  No, that is the union view's job (ADR-0102). Said so under Behaviour.
```

## Consequences

- The body gains syntax agents must not damage. The agent rule says so, and
  `verify` is the backstop: a mangled marker fails the gate, it is not lost.
- An agent's workflow gains one step, written into the agent rule: before
  starting work, `opys comments list --unresolved --turn=agent`, address each
  thread, reply with `opys comment reply`, and resolve or hand it back.
- Comment writes touch the document file and its `updated` time, so the board's
  modification heat counts a review as activity. That is wanted.
- The marker and section grammar join format.md and become a compatibility
  surface.
- A document with a long review history grows. `opys comments prune
  --resolved` drops resolved threads; git keeps them.

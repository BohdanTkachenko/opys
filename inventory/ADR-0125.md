# Comment threads live in the document they discuss

## Context

The loop opys serves is a human reviewing what agents wrote and an agent acting
on what the human said. Today the only way to say "this paragraph is wrong" from
the dashboard is to edit the body, which loses the distinction between the
document and the conversation about it, or to say it in a chat the next agent
will never see. Reviewers want what Google Docs and GitHub reviews give them: a
thread anchored to a passage, replies, and a resolved state. Agents need the
same threads as a queue they can poll: what is waiting on me?

Where the threads are stored decides everything else. Candidates:

1. A sidecar file per document (`FEAT-0001.comments.md` or a `_comments/` dir).
2. A server-side store owned by the node.
3. Frontmatter (a `comments` map).
4. The document body, in a reserved trailing section.

## Decision

1. **Threads are part of the document**, in a reserved `## Comments` section at
   the end of the body, written only through the CLI (and the node's typed
   actions, which call the same code). Files and git stay the only truth
   ([ADR-0051 — Files and git are the only truth; the server is a view](ADR-0051.md)): a thread travels with its branch, merges with git,
   is visible in a diff and greppable with `rg`, and needs no node to exist.
   A server-side store (2) would make the node a source of truth; a sidecar (1)
   doubles every relocation, retire and close; frontmatter (3) is closed,
   canonical and line-oriented, and multi-paragraph prose in YAML reads badly.
2. **Each thread is a block with a stable id, an anchor, a state and entries.**
   The id is local to the document (`C1`, `C2`, … never reused). The anchor is
   the section heading plus a quoted passage with a little surrounding text, the
   way annotation tools anchor to text that keeps changing; an anchor whose
   passage no longer exists is *outdated*, shown at the end of its section and
   never silently re-pinned. State is `open` or `resolved`. Each entry carries
   an author, an author *kind* (`human` or `agent`) and a UTC timestamp.
3. **Whose turn it is is derived, not stored**: an open thread whose last entry
   is by a human is the agent's turn, and vice versa. That is what
   `--turn=agent` filters on, and it cannot drift from the entries.
4. **The section is code-backed**, not an ordinary prose section: a new section
   kind owns its grammar, `verify` checks it (unique ids, known states, parsable
   entries — an outdated anchor is reported by `comments list`, not a verify
   failure), and the title/sections/blocks projections skip it so comments do
   not leak into `opys query` over body text. Prose linkify still runs inside
   comment text.
5. **Comments are opt-in per type** (`comments = true`), off for ephemeral types
   by default, because `close` deletes those documents and their threads with
   them; a closed document's open threads are listed by `close` before it runs.

## Consequences

- An agent's workflow gains one step, written into the agent rule: before
  starting work, `opys comments list --unresolved --turn=agent`, address each
  thread, reply, and resolve or hand it back.
- Comment writes touch the document file and its `updated` time, so the board's
  modification heat counts a review as activity. That is wanted.
- The section format joins format.md and becomes a compatibility surface.
- A document with a long review history grows. Resolved threads can be pruned
  with `opys comments prune --resolved`, since git keeps them.

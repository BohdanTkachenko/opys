# Priority is an opt-in declared field the board orders by

## Context

The founding stance is "deliberately not a task board — no sprints, assignees,
or priorities" (README, the skill, the agent instructions). It has served: the
corpus stays a knowledge inventory, not a project-management tool. But two
real needs arrived together. Agents working in loops need a *pull order* —
"take the most important open item first" — and the web UI's board needs a
stable, intentional card order within a column (it was id order, which is
creation order, which means the oldest item always squats on top).

The machinery for both already exists: `[fields.*]` declares typed frontmatter
fields, `set-field` writes them through the verify gate, and the board already
renders columns. The question was only whether priority becomes core semantics
or stays config.

## Decision

Priority is an **opt-in declared field**, never core semantics:

- A type that wants ordering declares `[types.X.fields.priority]` with
  `type = "int"`. Nothing in the engine knows the word "priority" — no rule,
  no lifecycle, no default. A project that never declares it has exactly the
  tool it had before.
- **Lower number = higher priority.** The board sorts a column ascending,
  unprioritised cards last, id as the tiebreak — the top card is the one to
  take next. Agents pull the same order with SQL (`opys query`) or
  `list --field`.
- The web UI writes it by drag: reordering a card within its column issues one
  verify-gated `set-field` (a midpoint between its new neighbours, gaps of 10,
  renumbering the column only when the numbers leave no room). On a type that
  never declared the field, the refusal *is* the onboarding: verify's message
  names the exact `opys.toml` block to add.
- The numbers are ranks, not severities: 10/20/30, not P0/P1. Nothing may
  attach meaning to specific values.

The default config does not declare it; this repo's own `opys.toml` does (on
feature/task/bug/chore), as does the demo.

## Consequences

- The "no priorities" line in the README, skill, and agent instructions is
  softened to "no sprints or assignees; priority only as an opt-in declared
  field" — the boundary that matters (no core PM semantics) survives intact.
- `DocSummary` carries `priority: Option<i64>` so the board can order without
  opening documents; anything non-integer reads as absent and sorts last.
- A reorder in a never-prioritised column renumbers every card in it — one
  `set-field` per card, each a full load/flush cycle. Accepted: it happens
  once per column, and afterwards reorders are one write.
- Two documents may share a priority (drag in one worktree, drag in another);
  the id tiebreak keeps the order deterministic and `verify` has nothing to
  say about it. If that ever needs an invariant, it becomes a `[[rules]]`
  entry, not engine code.

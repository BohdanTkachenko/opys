# Time-aware verify: stuck, visits, `--fix`

## Scope note: kobzar

All of this ships in opys, `--fix` included. The `--fix` transitions were
withdrawn on 2026-09-11 on the argument that only a dispatcher knows whether an
agent's session is still alive, and restored on 2026-09-23: an elapsed `ttl`
and a spent `max_visits` budget are deterministic — the document's own
`history` against a clock — so opys performs those moves itself, and a project
with no orchestrator is not left with observations it cannot act on. Session
liveness is the different signal, and that one is kobzar's, the separate
orchestration project; it acts sooner than the `ttl` through the ordinary
`set-status`, and opys does not wait for it. The reasoning is recorded in
[ADR-0101 — Verify observes time: stuck, visits, `--fix`, and exit code 3](ADR-0101.md)'s
scope note. The machine-readable form a dispatcher would want already exists:
`next --json` carries each item's observations.

The one part not built is the node's autofix (the last "Behaviour" bullet
below): it was dropped from
[TASK-0119 — opys-server: ref reader, occupancy in the union, `next` endpoint, autofix](TASK-0119.md)
during the withdrawal and has not been re-filed. Nothing here moves to kobzar.

Verify learns two observations that are not content problems ([ADR-0101 — Verify observes time: stuck, visits, `--fix`, and exit code 3](ADR-0101.md)): a
document that has sat in a status longer than its type allows, and one that has
re-entered a status more often than its type allows. It reports them apart from
problems, exits `3` when they are all it found, and with `--fix` performs the
configured transitions itself.

## Configuration

```toml
[types.task.ttl]
review      = "2d"                                # observed only, nothing to fix
in-progress = { after = "10m", then = "stuck" }   # a fast project; "2y" is
                                                  # equally valid elsewhere
[types.task.max_visits]
review = { limit = 3, then = "user-review" }

[types.task.transitions]
todo        = ["in-progress"]
in-progress = ["review", "stuck", "user-review"]   # …and the escalation edge
stuck       = ["in-progress", "todo"]   # the recovery edge autofix relies on
review      = ["in-progress", "user-review", "done"]
user-review = ["review", "in-progress"]
```

A `ttl` written as a bare duration (`review` above) is observed and nothing
more; the `{ after, then }` form is the one `--fix` performs.

`config validate` checks that every `ttl` target and every `then` target is a
declared status, and — where the type declares a status graph — that the graph
holds the three edges a fix and its refusal rely on: the fix edge `key -> then`,
the **recovery edge** `then -> key` (so a document flipped under a running agent
is one `set-status` from where it was), and, for `max_visits` only, the
**escalation edge** from every status that may enter the budgeted one to `then`
(the guard refuses the *entry*, so the escape it names must be legal from
wherever the document stands).

## Behaviour

- Stuck: the last history key is older than the status's `ttl`. Overflow: the
  number of history entries at a status **reaches** its `limit` — `limit = N`
  allows N entries, and the document that has made its N-th is at its limit. The
  guard and the observation trip together on purpose: since the guard caps a
  document at exactly `limit` entries, a strict "exceeds" reading would be
  unreachable through the CLI, and the refusal would be a dead end with no
  observation saying where the document should go. Both are one engine predicate
  used by verify, `next` and the flow view.
- `verify` prints observations in their own block after the problems, both on
  stderr, headed `verify: N observation(s)` (mirroring `verify: N problem(s)`).
  Exit `0` clean, `1` problems, `2` error, `3` only observations.
- `verify --fix` moves each stuck document to its `ttl` target and each
  overflowed one to its `then`, as ordinary transitions with history and the
  sync pass (skipped under `--no-sync`), then reports what remains. Nothing else
  is fixable. Every fix stays subject to the visit budget, the overflow one
  included: the guard counts entries into the status being *entered*, so
  exempting a fix could only waive the budget of the target it moves *to* —
  writing the one count the guard exists to prevent. A target whose own budget
  is spent lands in the refusals, naming its own `then`. And `--fix` stands down
  entirely while `config validate` has anything to say, since a fix is a move
  along the graph that check guards. Only a *config* problem stands it
  down: an unrelated content problem elsewhere in the corpus is reported and the
  fixes still run, so a node's autofix keeps unsticking documents in a corpus
  that has a finding. A run that fixes nothing writes nothing at all — neither
  the flush nor the sync pass.
- `OPYS_NOW` overrides the clock for tests and reproducible CI.
- In server mode the node verifies with `--fix` semantics by default;
  `autofix = false` in `server.toml` disables it (not yet built — see the scope
  note above; [TASK-0119 — opys-server: ref reader, occupancy in the union, `next` endpoint, autofix](TASK-0119.md)).

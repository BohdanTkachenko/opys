# Ship the web UI bundle in the crate tarball, not in git

## Context

[ADR-0078 — Svelte for the web UI; built assets are committed and drift-checked](ADR-0078.md)
committed `opys-server/ui/dist` to the tree and gated it with a CI job that
rebuilds the bundle and fails on drift. That decision was driven by a real and
unchanged constraint: `cargo install opys`, docs.rs (whose policy is that network
access is never enabled for any crate) and the Nix `buildRustPackage` sandbox all
build with **no Node and no network**, so nothing may fetch or compile the UI
during the crate build.

What that decision got wrong was not the constraint but the space of answers. It
framed the choice as three-wide — commit the output, download at build time, or
sidestep `cargo install` — and picked the first. A survey of how the ecosystem
actually solves this found a fourth shape it never considered, and the three it
did consider break down as:

- **No pipeline at all.** mdBook embeds `front-end/js/book.js` and a vendored
  `highlight.js` with `include_bytes!`; there is no bundler and no
  `package.json`. Those files are *sources*, so nothing can drift. This is the
  Preact-plus-htm fallback the superseded ADR named. Measured against this UI it
  does not pay: 3,609 lines across six views and five rune-based stores would have to be
  rewritten with no UI test suite to catch regressions, the vendored
  `preact.module.js`/`htm.module.js` are themselves committed build output (so
  the objection survives), and an unminified bundle is *larger* than the 88 kB
  Svelte emits.
- **Download at build time.** Meilisearch's `build.rs` is entirely
  `#[cfg(feature = "mini-dashboard")]` and fetches from a URL in package
  metadata; with the feature off `main()` is empty and there is no UI. That is
  precisely the trade that was rejected before, and rightly.
- **Download at runtime.** Stalwart pulls its webadmin from GitHub releases when
  the server starts — notably even though that UI is Leptos, i.e. Rust, which
  shows a WASM frontend does not dodge the problem either. Rejected here for
  opys specifically: it breaks offline use of a tool whose whole premise is local
  files, adds a network trust root to an origin that serves write actions,
  weakens `ui-build`'s zero-external-requests audit from "these bytes" to "some
  bytes on a server", and makes the Nix story worse rather than better.
- **Ship it in the published artifact.** Never considered. Cargo's
  `include` overrides `.gitignore` when packaging, so a gitignored `dist/` can
  still reach crates.io inside the `.crate` tarball. Verified empirically before
  adopting: a scratch crate with `dist/` gitignored and `include = ["dist/**"]`
  packages the file that git does not track.

The remaining question was who pays. Committing the bundle costs reviewers a
generated directory and every UI change a two-step commit; the tarball costs
everyone building from source a Node toolchain. For a project that is largely
solo and already has Node in its devShell, those are one-time engineering costs
(a Nix derivation, a few CI steps) rather than ongoing friction.

## Decision

`opys-server/ui/dist` is **gitignored and generated**. It reaches consumers three
ways, and all three build the same bytes:

- **crates.io** — `include` in `opys-server/Cargo.toml` puts `ui/dist/**` in the
  tarball, so `cargo install opys` and docs.rs are unaffected and still never run
  Node. The release job builds the bundle before `cargo publish`.
- **Nix** — a `buildNpmPackage` derivation (`mkUi` in `flake.nix`, exposed as
  `packages.opys-ui`) builds the bundle, and `postPatch` plants it in the Rust
  derivation. `npmDepsHash` makes the dependency fetch a fixed-output derivation
  rather than arbitrary network access, which is what keeps this legal in the
  sandbox.
- **A source checkout** — `ui-build`, as before.

Every `include` pattern is anchored with a leading `/`. They are gitignore-style,
so an unanchored `README.md` matches at any depth and drags one in from every
package under `ui/node_modules`. `cargo package --list -p opys-server` is the
check, and CI runs it.

A **`web-ui` cargo feature, on by default**, gates the embedding. `cargo install
opys`, docs.rs and the Nix package therefore all ship a UI; a contributor who
does not want a Node toolchain builds with `--no-default-features` and gets a
node whose API is complete and whose two UI routes answer **501** — not 404,
which would send an operator hunting for a typo instead of looking at their
build. `opys` forwards the feature and takes `default-features = false` on the
dependency, because cargo applies `--no-default-features` per package and
opys-server would otherwise keep its own default regardless.

`build.rs` still never runs Node and never touches the network. With `web-ui` on
and no bundle present it fails, naming **both** remedies — build it, or disable
the feature — because there are genuinely two audiences and picking one sends
the other the wrong way. It must never degrade silently to a UI-less binary.

The drift gate is **removed**: with nothing committed there is nothing to drift.
`ui-build` keeps its zero-external-requests audit, which now runs on every build
rather than only in CI.

## Consequences

- Building from a git checkout now needs Node. Every cargo CI job gains a bundle
  build, contributors need npm, and the Nix package carries an `npmDepsHash` to
  re-hash whenever `package-lock.json` changes. This is the cost of the decision,
  paid by everyone who builds rather than by everyone who reviews.
- The generated directory, its `linguist-generated` attributes, the drift job and
  the two-step commit all go away.
- Two build configurations must now both work, so CI tests both. The UI-less path
  is covered by unit tests in `src/assets.rs` (asserting the table really is
  empty, so dropping the feature cannot silently keep shipping a bundle) and by a
  `tests/api.rs` case pinning the 501s. `tests/assets.rs` is gated on the feature
  rather than made tolerant of an empty table: a test that passes whether or not
  the thing it checks exists is worse than no test.
- Source EOL pinning matters *more*, not less. Three paths build the bundle
  independently and must agree; `eol=lf` on `opys-server/ui/**` is what stops a
  CRLF checkout from compiling different bytes. Verified: the Nix derivation
  (Node 24) and the devShell (Node 22) produce byte-identical output.
- The bundle's size is still worth watching, since it still ships inside every
  binary — but it is no longer visible in the tree, so nothing surfaces a
  regression automatically. `ui-build` prints the byte count on every run.
- [ADR-0078 — Svelte for the web UI; built assets are committed and drift-checked](ADR-0078.md)
  is superseded. Its choice of **Svelte 5**, its no-SvelteKit scope, and its
  zero-external-requests hard rule all stand unchanged; only the delivery of the
  built output changes. Preact plus htm remains the named fallback if the
  pipeline ever proves more trouble than it saves.

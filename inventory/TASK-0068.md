# engine: extract print-free cores for block/unblock

The server's action endpoint ([TASK-0072 — opys-server: action endpoint through the command cores](TASK-0072.md)) calls engine command cores directly
and must never print to the server process's stdout. Audit result: `new`,
`set-status`, `tag`, and `close` already follow the pattern — a print-free
`core(prj, store, …)` plus a `run(ctx, …)` wrapper that loops ids, calls the
core, and prints. **Only `block`/`unblock` (`src/commands/block.rs`) have their
logic inline in `run` with `println!`.**

Spec — a mechanical refactor, no behavior change:

- In `src/commands/block.rs`, extract `pub fn block_core(prj, store, id, by) ->
  Result<()>` and `pub fn unblock_core(prj, store, id, by) -> Result<()>`
  holding everything the current `block`/`unblock` fns do per id except the
  `println!` (both link directions, the auto-`blocked` status set / revert,
  touch). The existing `pub fn block`/`pub fn unblock` become thin wrappers:
  resolve the id list, call the core per id, print the same lines as today.
- Naming: `block_core`/`unblock_core` (the module already has two entry points,
  so a single `core` name doesn't fit).
- Behavior is pinned by the existing integration tests
  (`block_links_both_directions_and_sets_blocked_status`,
  `unblock_removes_link_and_reverts_status`,
  `unblock_restores_pre_block_status`,
  `unblock_without_in_progress_falls_back_to_default` in `opys/tests/cli.rs`)
  — they must pass unmodified. Do not change any output string, exit code, or
  file byte.
- This is Apache-side engine work: keep it generic, no server-specific code or
  deps in the engine.

# Lifecycle is config: transitions, history, derived blocked, priority

## Context

Four things about the lifecycle are fixed in code today. Any status may move to
any status; the only guard is that a terminal status is reached through `close`.
Blocked is a *status*: `block` auto-sets it, remembers the previous one in
`blocked_from`, and a free-text `blocked_reason` counts as blocked too. Priority
is an opt-in `int` field ([ADR-0095 — Priority is an opt-in declared field the board orders by](ADR-0095.md))
that only the board reads; nothing in the CLI orders by it.
And `new --status` creates a document at any status, skipping whatever ordering
a type implies.

Two of those were principled: the inventory records intent, not scheduling, and a
task board was explicitly out of scope. The others were defaults nobody had a
reason to revisit. The reason is [FEAT-0109 — Flow graph view: statuses as nodes, agents as loops](FEAT-0109.md): an orchestrator that spawns one agent
loop per status, each loop picking the next unblocked item, doing that stage's
work, and moving the document on. That needs legal transitions (an agent may only
move a document along declared edges), an ordering (a hundred tasks need one),
blockedness that follows from the blocker graph rather than from a flag someone
set, and a record of transitions so verify can check them and so time-based
observations ([ADR-0101 — Verify observes time: stuck, visits, `--fix`, and exit code 3](ADR-0101.md)) have a clock.

Every one of those is worth having without loops. A state machine that
validates status changes is a legitimate guard on its own. An ordering is
legitimate at a hundred tasks. And verify today checks a snapshot while a
transition is an event, so a document whose status jumped straight to done by
hand is invisible to the CI gate.

## Decision

1. **Transitions are per-type config.** `[types.X.transitions]` maps a status to
   the statuses it may move to. Absent, the type keeps today's any-to-any rule,
   byte-identically. `default_status` is the initial state. `terminal_statuses`
   keeps its meaning: reached only through `close`. `set-status` refuses an
   undeclared edge and names the allowed targets. `block` and `unblock` no
   longer touch status, so they need no edges.

2. **Every transition is recorded.** A reserved, auto-maintained frontmatter key
   `history` holds a map of UTC RFC3339 timestamp to status, one entry per
   line, sorted by key. Keys carry sub-second precision and always end in `Z`,
   so lexical order is chronological and two transitions inside one second
   cannot collide. `new` writes the first entry, `set-status` and `verify --fix`
   append, `import` seeds one entry at the status it was given. Verify checks
   that the last entry equals `status`, that consecutive entries are declared
   edges when the type declares any, that keys strictly increase, and that
   `created` equals the first key when both are present. The state machine is
   thereby a write-time guard *and* a CI check. Hand edits remain possible;
   verify catches their shape, and git (the `history` command) is the audit.

3. **Blocked is derived, never stored.** A document is blocked iff it has a live
   `blocked_by` entry: not struck through, resolving to a document whose status
   is not in that document's type's `releases_blocks` set. Ephemeral types
   release by construction, because `close` deletes the blocker and strikes the
   entry; permanent types declare the set (a feature releases at `implemented`,
   `wontfix`, `archived`). The `blocked` status, `blocked_from`, `blocked_reason`
   and the auto-set on `block` are removed. Everything that blocks is a
   document: "waiting on a vendor" is a chore.

4. **Priority is the `int` field of [ADR-0095 — Priority is an opt-in declared field the board orders by](ADR-0095.md),
   and `next` orders by it.** Nothing new is declared: a type that wants
   ordering declares `priority` (`type = "int"`, lower = higher) exactly as the
   board already requires, and the shipped config has it on feature, task, bug
   and chore. A type's `order_by` names the tiebreak chain, by default
   `priority`, then the count of live documents the item blocks, then lowest
   id; an unprioritised document sorts after every prioritised one, as on the
   board. Effective priority is the smallest number over the item and
   everything it transitively blocks, so a task at 30 holding up one at 1
   sorts as 1. An integer rather than a ranked enum because it is already
   shipped and more flexible: a slot between two neighbours always exists, and
   the board's drag-to-reorder and `next` read the same number.

5. **`new --status` is removed.** A document starts at its type's initial state.
   `import` is the one seam that seeds elsewhere.

## Consequences

- format.md changes in three places: the any-to-any sentence, the blockers
  section, and the reserved keys table (`history` in, `blocked_from` out);
  [ADR-0095 — Priority is an opt-in declared field the board orders by](ADR-0095.md) already carved
  priority out of the "what never goes in a document" paragraph. Code and
  format.md move in the same task, per the repository rule.
- The shipped config loses `blocked` from `task`/`bug`/`chore`, loses the
  `require_any` blocked rule and the `blocked_reason` fields, and gains
  `transitions`, `releases_blocks` and `order_by` (`priority` is already there).
- The byte-identity pin in `opys/tests/cli.rs` changes across the board, because
  every `new` now writes a history entry. That is deliberate and should be said
  in the commit, so nobody reads it as the [FEAT-0058 — opys-server: the always-on node](FEAT-0058.md) rule being broken.
- History conflicts at merge are rare (a sequential handoff on one branch never
  conflicts; competing branches merge one winner) and, when they happen, are
  real information: main moved the same document. Sync cannot rebuild history
  from ground truth the way it rebuilds references, so verify reports a botched
  resolution rather than repairing it.
- The serializer reuses the one-entry-per-line map formatter of the relation
  maps; keys contain colons and are quoted. A list form would have been inlined
  onto one ever-growing line.
- This repository's own inventory holds documents at `blocked` with
  `blocked_from`, and no document has `history`. Migration is a document an
  agent executes once ([TASK-0110 — engine: the history map and UTC sub-second timestamps](TASK-0110.md)), seeding history from the `history` command
  where git has it and from `created` otherwise, not a tool.
- [ADR-0066 — SQL is the internal working representation; markdown stays the truth](ADR-0066.md)'s "raw DML is not lifecycle" sharp edge becomes untenable once
  transitions carry history; [ADR-0100 — SQL is read-only; every write is a lifecycle command](ADR-0100.md) closes it.

# A corpus activity feed: opens, not just writes

The board's heat signature shows *writes*. The next step is showing *reads*:
a corpus activity feed — "opened [FEAT-0087 — The terminal-modern web UI redesign](FEAT-0087.md)", "edited TASK-0012" — so a person
watching the dashboard can see what parts of the project memory their agents
are touching in real time.

File access times are not the way: Linux defaults to `relatime` (atime moves at
most once a day) and many machines mount `noatime`, so "recently opened" via
`stat` is false on most systems. The honest sources are:

- the node's own notify watcher, extended to subscribe to open/access events
  (inotify `IN_OPEN`) where the platform offers them — noisy, needs debouncing
  and self-filtering (the node's own reloads must not count as activity);
- the node's own API reads (`GET /doc`) — a browser or MCP client opening a
  document through the node is activity the node already sees for free;
- CLI invocations, if `opys show` ever reports to a running node (it must never
  *require* one).

The feed would be a ring buffer per corpus, an `/api/activity` endpoint, an
event-stream message, and a sidebar panel — plus feeding the board's heat so
opened-but-unwritten documents warm faintly too.

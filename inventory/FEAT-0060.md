# Flow graph view: statuses as nodes, documents on them

## Scope

**Branch progress.** The flow now presents labelled status/title versions from
served worktrees and the existing ref reader, including uncommitted worktree
changes and branches with no checkout. Primary documents and primary `next`
picks remain intact. Identical versions retain every source label, branch-only
tickets remain visible, and errors are unknown rather than empty sources. The
page distinguishes ticket counts from version counts and refetches for any
member's reload, ref movement or reconnect. Expensive pure read calculations
run outside the inventory worker on immutable reload snapshots. Cached lists,
counts and calculation inputs remain available while a reload runs, publishing
the replacement together after success. Atomic config replacement is watched so
checkout changes update the view repeatedly.

**Claim activity.** The lifecycle sidebar lists explicitly claimed, available
cards without requiring a stage selection, with document links, stage roles,
claim holders and activity ages. Claimed stages carry a visible count, and
their inspector lists claimed cards first. The activity list and counts follow
the visible document types and exclude unavailable copies. Claim updates do
not reposition the graph. Stage roles name the configured queues; they do not
identify a worker or assert that its process is alive.

The **agents overlay** beyond recorded claims belongs to an orchestrator, not
to opys: process liveness, worker capacity, harvesting stuck items and the
reference loop. What stays here is the graph
itself — statuses as nodes, the edges the transitions declare, and the
documents placed on them
([ADR-0027 — Files and git are the only truth; the server is a view](ADR-0027.md)).

**Status counts.** Each status and its inspector show total cards for the
visible types, or `Empty` when there are none. Amber lock badges say `All blocked`
or name the blocked count; mixed stages also show the unblocked count. Stages
without blockers have no blocked badge. Muted badges preserve unknown blocker
states, and claims keep their separate green indicator. Repeated versions count
once per ticket; only authoritative documents establish blocker state. Space for
badges is reserved so blocker changes do not reposition the graph.

**Executed on the opys side (2026-09-14).** What shipped is the graph and the
documents on it: one node per distinct status name, edges from the union of
every type's `transitions`, each node's top items taken from `next::pick` in
`next` order with blocked and orphaned ones counted and reasoned rather than
listed, an undeclared status drawn and marked, and a layered left-to-right
drawing with dashed returns for the cycles. Three of the Shape bullets describe
things that did not ship here and belong to the agents overlay: the per-type
`[types.X.limits]` table (the cap is the endpoint's `?n=`, default 5),
occupancy chips on an item, and the `human = true` gate. The test plan below
marks them.

The web UI gains a view where each node is a status and each node shows the
next few items an agent at that stage would pick. It is the kanban board drawn
as the graph the transitions declare, with a capacity per node, and it is the
picture an orchestrator runs against: one loop per node, each taking the top of
its node, doing that stage's work, and moving the document along an edge.

It is a view. The runner is not opys. Claude Code's loop command, a cron job,
or a script drive it, and the skill ships a reference loop one screen long.

## Shape

- One graph per project. Statuses with the same name across types share a node;
  the edges are the union of every type's transitions, so this repository's own
  config draws three components: work items, features, decisions (the shipped
  default has no `adr` type, and draws two). Guards stay per type.
- Each node shows up to `[types.X.limits]` items per type, ordered by
  `next::pick` ([FEAT-0057 — `opys next`: the pick oracle](FEAT-0057.md)), so the view and the CLI show the same items. Blocked
  items are counted and greyed, never listed.
- Occupancy is drawn on the item: which refs hold it at another status, stuck
  ones marked. This comes from the union with the node's ref reader columns,
  so it includes branches nobody has checked out.
- A node with no agent loop is a human's. The view cannot know that, so a node
  declared `human = true` in `[types.X.limits]` is drawn as a gate. The skill
  says why one belongs before any status that lands on main.
- Clicking an item opens the document view; the action bar already offers
  `set-status` along declared edges only.

## Manual verification

### Setup
- A project with the shipped config, a dozen tasks across statuses, two with
  blockers, and one branch without a worktree holding a task at `review`.

### Procedure
1. Open the flow view and compare each node's Ready next primary items with `opys next --status <s>`. Inspect the other branch's labelled version at `review`.
2. Block one of the listed items from the CLI and watch it drop from the node.
3. Set `OPYS_NOW` on the node far in the future, restart, and look for the stuck mark.
4. Claim a card through the project's runner. Check its stage count and the
   sidebar's In progress list, open its document, and use its stage button to
   inspect that status. Hide its document type, then show it and release its
   claim.

### Expectations
- Node items match the CLI, item for item and in order.
- The blocked item leaves the list and the node's blocked count rises by one.
- The branch-held task shows its labelled progress separately from primary, with its branch source. Step 3 marks primary observations through the server predicate; branch observation marks remain uncovered below.
- Explicitly claimed cards appear without selecting a stage. Type filters and
  claim release update both the list and stage counts without moving the graph.

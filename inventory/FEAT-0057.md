# `opys next`: the pick oracle

## Scope

The **policy** options are an orchestrator's, not opys's:
concurrency caps, occupancy rules (`--exclude-occupied`), harness affinity, cost
budgets and lease logic. What opys provides is a deterministic pick oracle over
main — unblocked, at a pickable status, ordered by the type's chain, with
`--explain` — which an orchestrator wraps
([ADR-0027 — Files and git are the only truth; the server is a view](ADR-0027.md)).

**Executed on the opys side (2026-09-14).** What shipped is the deterministic
oracle: pickability, orphans with their reason, the `order_by` ranking shared
with `list --sort`, `--explain`, and the stable `opys.next/1` payload — served
identically by the CLI and by the node's endpoint. `next` reads **no git at
all**: pickability is decided on the corpus the command runs in, so the "what
the branches say" half of the sentence below, and the last test-plan item with
it, describe an orchestrator's job rather than opys's.

The question every loop asks first is "what should I work on". `opys next`
answers it from the inventory, with no server and no runner: the top items of a
status, ordered by the type's chain, minus everything blocked, plus what the
branches say about each one.

There is deliberately no claim. An orchestrator spawns agents and decides
whether an item that is already in progress on some branch is taken or is fair
game for a competing attempt. opys reports; the orchestrator chooses. That is
also why the output is JSON when asked: it is parsed, not read.

## Behaviour

- `opys next --status <s> [--type <t>] [-n N] [--json]` lists the first N
  documents at that status, ordered by their type's `order_by` chain with
  effective priority ([FEAT-0055 — Configured lifecycle: transitions, history, derived blocked, priority](FEAT-0055.md)), excluding blocked ones.
- Pickability is evaluated on **main's** inventory, the corpus the command runs
  in. A blocker closed on a branch does not release anything ([ADR-0053 — Branches are progress, main is truth](ADR-0053.md)).
- A document whose `requires_link` target is at a status in that type's
  `releases_blocks` set, such as a task under a `wontfix` feature, is not
  pickable and is listed under a separate `orphaned` key.
- `--explain` says why each listed document was picked and, for a document the
  caller names, why it was not: blocked by a live blocker, at another status,
  orphaned, or ordered behind others.
- Occupancy, `--exclude-occupied` and a per-status cap read from config are
  **an orchestrator's**, not opys's: which of several eligible documents an agent should
  take, and whether an occupied one is fair game, is policy. `next` answers the
  deterministic question and an orchestrator wraps it.
- The selection is an engine function, `next::pick`, called by the CLI and by
  the node's endpoint, so the two cannot drift.

# Role queues: everything waiting on a role, across projects

A person opens the node's **role page**, picks a role (`human`, say) and sees
every document waiting on that role in every project the node serves: the
specs to sign off, the decisions to make, and whatever the automation could
not handle. An agent sets `OPYS_ROLE=agent-codex`, runs `opys queue`, and gets
the same answer for its own role in one project. The decisions behind it are in
[ADR-0068 — Statuses are owned by declared roles; a role is only a name](ADR-0068.md): roles are plain declared names, statuses are owned by roles,
a document may override its owner for one step, and an `escalate_to` role
receives what needs intervention.

## Scope

**Executed.** Queue items add a true-only `owner_override` flag so the UI can
mark explicit overrides even when they equal the status owner. A missing
`since` is omitted when neither history nor created exists. Overridden
documents with undeclared statuses get groups after the type's declared
statuses, in corpus order; a missing status uses an empty name, keeping
malformed work visible to its role. A failed project remains an error on
`/api/roles/{role}` when its declarations cannot be read: only a successful
snapshot can establish that it does not declare the role. An explicit owner
in `apply` is restored before target rules run, so guards see the completed
visit rather than the cleared intermediate state.

**In scope:**
- the config (`[roles]`, `[types.X.owners]`, `escalate_to`, the `role` field
  type and the `owner` override);
- one engine module that reads all of it;
- `opys queue`, `opys next --role` and `opys list --waiting-on`;
- the node's per-project and cross-project endpoints;
- the role page;
- owners shown on the flow view and the document view;
- the documentation.

**Out of scope:**
- Comment threads addressed to roles: that is [ADR-0068 — Statuses are owned by declared roles; a role is only a name](ADR-0068.md) decision 6, and [FEAT-0063 — Inline comment threads: a human-agent review loop](FEAT-0063.md)
  implements it. Once it lands, `opys.queue/1` gains a `threads` key. This
  feature leaves no placeholder for it.
- Notifications, authentication of a role choice, and any inference about
  which statuses a person works.
- Which agent or model works a role.
- Migrating any project's own config to roles.

**Hard constraint:** a project that declares no roles sees no change. Every
existing command's output stays byte-identical, and `opys/tests/cli.rs` must
pass untouched. Every new payload field is omitted when it is empty or absent.

## Behaviour

### Config

```toml
escalate_to = "human"                  # optional, top level

[roles.human]
kind = "human"                             # optional worker metadata
description = "Dan: sign-offs and decisions"   # optional

[roles.agent-claude]
[roles.agent-codex]

[types.task.owners]                     # optional, per type
todo          = "agent-claude"          # one role…
ready         = ["agent-codex", "agent-claude"]   # …or several
needs-human   = "human"
landed        = []                      # deliberately waits on no one

[types.task.fields.owner]               # optional: the per-document override
type = "role"
```

A role table accepts optional `description` and `kind` (`human`, `agent`, or
`automation`); any other key is a parse error,
like every other closed table in the config. An `owners` value may be a string
or a list; both are normalised to a list.

`config validate` (`ProjectConfig::validate`) reports each of these as a
problem, naming the type, the key and the legal values:
- a role name that does not match `^[a-z][a-z0-9-]*$`;
- an `owners` key that is not one of the type's statuses;
- an `owners` key that is a terminal status;
- an `owners` value naming an undeclared role, or naming the same role twice;
- a type with an `owners` map that leaves out a non-terminal status (`[]` is
  how a type says "nobody");
- `escalate_to` naming an undeclared role;
- a field of `type = "role"` in a project that declares no roles;
- a field named `owner` that is not `type = "role"`, on a type that declares
  `owners`.

`verify` reports a `role` field whose value is not a declared role.

### Effective owners

A document's **effective owners** are:
1. its `owner` field, if its type declares one with type `role` and the
   document sets it;
2. otherwise its type's `owners` entry for its current status;
3. otherwise nobody (an unowned type, or `[]`).

A document **waits on** R when R is among its effective owners.

**Clearing the override.** Every move to a *different* status removes `owner`
from the document:
- `set-status`;
- `apply --status`;
- `verify --fix`;
- the node's status action, including drag-to-change-status.

The one exception: `apply --status S --field owner=R` keeps R, because the
override is written for the status the same command enters. A same-status
`set-status`, which appends a history entry and changes nothing else, keeps
the override. `import` writes whatever it is given.

### `opys next --role`

- `--role R` narrows the existing oracle to documents that wait on R.
  `--status` stays required.
- An undeclared role is a usage error (exit 2) that lists the declared roles.
  The node returns it as a 400, the way it does for a bad status.
- `--explain <ID>` gains one reason, "waits on X, not R". It is checked after
  the type and status reasons and before the orphaned reason.
- `opys.next/1` gains the `role` echo, and each item gains `owners` (its
  effective owners). Both are omitted when empty or absent, so the payload
  without `--role`, in a project without roles, is byte-identical to today's.

### `opys queue [<role>]`

Everything waiting on one role in this project.

- **Role.** The argument; else `OPYS_ROLE`. With neither, or with an
  undeclared role, it is a usage error that lists the declared roles.
- **Options.** `--type T` narrows to one type. `-n N` caps the items of each
  group and defaults to `next`'s default; the attention list is never
  truncated. `--json` prints `opys.queue/1`.
- **Read-only.** Like `next`: no sync, no flush, no git, and exit 0 for every
  answer, empty included.

**Groups.** There is one group per (type, status) that R owns. Types come in
declaration order (`pcfg.types.names()`), and each type's statuses in its
`statuses` order. A document whose `owner` override names R also produces
a group for its (type, status), even when R does not own that status. Such a
group is marked `owned: false`, and the document appears only in R's queue,
not in its status owners' queues.

Each group splits its documents with `next`'s own precedence (orphaned, then
blocked, then pickable):
- `items`: the pickable documents, in `next` order, each a `next` item plus
  `since`, the instant of its last `history` entry (else `created`).
- `blocked`: every live-blocked document, with its live blockers' ids.
- `orphaned`: `next`'s orphans, with their reasons.

For an owned group, `items` before the limit are exactly the items of
`next --status S --type T --role R`, field for field.

**Attention.** It is non-empty only when R is the project's `escalate_to`.
Each document that needs intervention is listed once, with every reason it
has:
- `orphaned`, with `next`'s reason;
- `stuck` or `overflowed`, from `observe`, with the same wording `verify` uses;
- `problem`, a `verify` finding that carries this document's id.

Findings with no document id go into a separate `project_problems` list of
messages. Attention entries are ordered by id number. A document listed
under attention also stays in its status group.

**`total`** is the number of distinct documents across every group's pickable
items (before the limit) and the attention list.

```json
{
  "schema": "opys.queue/1",
  "role": "human",
  "type": null,
  "limit": 10,
  "total": 3,
  "groups": [
    {
      "type": "task", "status": "spec-approval", "owners": ["human"], "owned": true,
      "total": 1,
      "items": [ { "id": "TASK-0812", "…": "the next item fields", "since": "2026-10-17T21:04:11.000000Z" } ],
      "blocked": [ { "id": "TASK-0844", "title": "…", "path": "…", "blocked_by": ["TASK-0821"] } ],
      "orphaned": []
    }
  ],
  "attention": [
    { "id": "TASK-0790", "type": "task", "title": "…", "status": "implementing", "path": "…",
      "reasons": [ { "kind": "stuck", "message": "…" } ] }
  ],
  "project_problems": []
}
```

In JSON, every owned group is present even when it is empty, so a consumer can
tell "nothing waiting" from "not owned". The text output prints only groups
that have something in them:

```
human: 3 waiting

task · spec-approval  (human)
  TASK-0812  Piece verification spec                 since 2026-10-17  p20
task · needs-human  (human)
  TASK-0830  Pick the archive.org rate-limit policy  since 2026-10-18
  1 blocked: TASK-0844 (by TASK-0821)

attention  (escalate_to)
  TASK-0790  implementing  stuck: …
```

With nothing waiting, it prints `human: nothing waiting`.

### `opys list --waiting-on <role>`

`--waiting-on R` filters `list` to documents that wait on R. It combines with
the other filters and with `--format ids`, so a bulk command can take a role's
documents through a pipe. Attention is not part of it. An undeclared role is a
usage error.

### The node

- `GET /api/projects/{key}/queue/{role}` returns `opys.queue/1` from the group's
  primary corpus (resolved by `api::primary_cid`, like `/next` and `/flow`).
  It is byte-identical to `opys queue <role> --json` run in that corpus. A role
  the project does not declare is a 404 that names the project and the role.
  `?type=` and `?n=` mirror the CLI.
- `GET /api/roles` lists every role declared by any served project, merged by
  exact name and sorted by name. Each role carries
  `projects: [{key, label, description, total}]` and its overall `total`. A
  project that could not be asked appears under `errors: [{key, label, error}]`
  and is never reported as zero. Schema: `opys.roles/1`.
- `GET /api/roles/{role}` returns
  `{schema: "opys.role/1", role, projects: [...]}`. Each entry is either
  `{key, label, queue}` or `{key, label, error}`. Projects that do not declare
  the role are left out, and the rest come in the sidebar's project order.
  An `Err` from a corpus stays an error entry, never an empty queue, for the
  same reason as `union.rs`.
- The attention list should reuse the corpus actor's cached verify findings
  instead of running `collect_findings` again on every request. The CLI
  computes them fresh.
- `FlowNode` gains `owners`: the union of the owners that each declaring type
  gives that status, in type declaration order, de-duplicated, and omitted
  when empty.
- `DocView` gains `owners` (the effective owners) and `owner_override` (true
  when they come from the field).
- There are no new typed actions. The override is written with the existing
  set-field action. The document view renders a `role` field as a select of
  the declared roles. Status moves clear the override through the shared CLI
  path.
- There is no new event. The page refetches on `corpus-reloaded` for any
  primary corpus, the way `Flow.svelte` does.

### The role page

- **Routes.** `#/role/<name>` shows a role. `#/role` opens the role last
  chosen in this browser (kept in `localStorage`, with every access wrapped
  in try/catch), or else a picker.
- **Sidebar.** A **Role queues** entry sits above the project list. It shows
  the remembered role's total as a badge and links to `#/role`.
- **Header.** A role picker lists every role from `/api/roles`, each with its
  total and its descriptions, and switching role changes the hash.
- **Attention.** When attention is present, it comes first, per project, with
  each document's reasons.
- **Projects.** Then one section per project with something waiting: the
  project label links to its board, followed by its groups. A group heading
  shows the type and status, owner chips and "N waiting · M blocked". Each
  item row shows the id, title, a relative `since` ("3 days"), the priority,
  the observation marks and an override mark. Clicking a row opens the
  document view. Blocked documents are folded under their group.
- **Errors.** A project that errored shows as an error row, never as an empty
  section.
- **Empty state.** "Nothing is waiting on `<role>`."
- **Keyboard.** `j`/`k` move between rows and `Enter` opens one, reusing the
  board's keyboard navigation ([FEAT-0048 — Keyboard navigation on the board: columns, cards, projects](FEAT-0048.md)).
- **Narrow screens.** One column, like the rest of the shell ([FEAT-0047 — The narrow-screen shell folds the sidebar into a bar](FEAT-0047.md)).
- **Pure module.** Grouping, ordering and the relative `since` formatting
  live in a pure `ui/src/lib/queue.js`, tested under `node --test` like
  `flow.js`.
- **Flow view.** The flow view draws each node's owners as chips. The document
  view shows "Waiting on: …" beside the status, and marks an override.

## Manual verification

### Setup
- A node serving two projects. Project A declares `human`, `agent-claude` and
  `agent-codex`, with task statuses owned roughly as in [ADR-0068 — Statuses are owned by declared roles; a role is only a name](ADR-0068.md), an `owner`
  field and `escalate_to = "human"`. Project B declares `human`, with a
  `review` status owned by `human`.
- Project A has a task at `spec-approval`, one at `needs-human`, one at
  `review` with `owner = agent-codex`, one blocked task at `needs-human`, and
  one task at `implementing` with a short `ttl`. Project B has a document at
  `review`.

### Procedure
1. Open `#/role`, pick `human`, and compare each project's section with
   `opys queue human` run in that project.
2. Move the `spec-approval` task on from its document view, and watch it leave
   the page.
3. From the document view, set `owner = human` on the `review` task, then move
   it to its next status, and check that the override is gone.
4. Restart the node with `OPYS_NOW` past the `implementing` task's ttl.
5. Run `OPYS_ROLE=agent-codex opys queue` in project A.

### Expectations
- The page shows both projects under `human`, matching the CLI item for item;
  the blocked task is folded under its group.
- After step 2 the task disappears without a reload, and the badge count drops
  by one.
- In step 3 the task appears on `human`'s page while the override is set, and
  after the move it waits on its new status's owners, with no `owner` field.
- After step 4 the `implementing` task is listed under attention as stuck.
- Step 5 lists the queues `agent-codex` owns, and nothing that waits only on
  `human`.


## Role kinds and initial selection

[ADR-0072 — Role kinds describe workers and choose the initial queue](ADR-0072.md)
extends role metadata with optional human, agent, and automation kinds. Existing
untyped roles remain unknown rather than being classified by name. Project
pages retain their local kind; merged roles expose one only when all declaring
projects agree. The picker shows the kind and defaults to a remembered available
role per project (separate from the cross-project choice), then the first human
role, then the first available role. Group the dropdown with humans first,
then agents, automation, and unspecified roles. An explicit
role URL takes precedence.

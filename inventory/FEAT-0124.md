# Document history and diffs in the web UI

The document view shows a card as it is now and nothing else. Reviewing what an
agent changed means leaving the dashboard for `git log -p`, which knows nothing
about relocations (a status change moves the file) and shows frontmatter churn
and body edits as one undifferentiated hunk.

The document view gains a **History** panel: every commit in which the
document's content changed, newest first, each with the commit's full subject
line (and the body on expand), author, date and short hash, plus the status at
that revision. Picking any revision diffs it against the working copy; picking
two diffs them against each other. The diff renders **side by side** or
**inline**, a toggle remembered per browser, and is split the way a reader
thinks about a card: frontmatter fields as a key-by-key table (status
`todo → in-progress`, a tag added, a relation struck), then the body section by
section, so an unchanged section folds to its heading.

## Behaviour

- The timeline comes from the engine's git reader ([FEAT-0107 — Branch reader: the in-binary git adapter](FEAT-0107.md)), not from
  shelling out, and follows the document across relocations by id — the same
  walk `opys history` does. Each revision is attributed to the commit that
  *introduced* it, which is the hole that keeps [FEAT-0019 — history: git status timeline](FEAT-0019.md) partial; this
  feature closes it rather than building on it.
- jj: a colocated jj repository is a git repository and works as is; jj change
  ids are shown next to the commit when `.jj/` is present. A non-colocated jj
  repo, and the jj operation log, are out of scope.
- The node grows two read endpoints: `GET /api/corpus/{cid}/doc/{id}/history`
  (the revision list) and `GET /api/corpus/{cid}/doc/{id}/at/{commit}` (the
  document text at a revision, decoded through the real parser). The diff is
  computed by the engine and served structured (frontmatter changes plus
  per-section line hunks), so the CLI can print the same thing.
- CLI parity: `opys history <id>` gains commit subjects; `opys diff <id>
  [<rev>] [<rev>]` prints the same structured diff, defaulting to the last
  revision against the working copy.
- Revisions on other branches stay the union view's job ([ADR-0102 — Branches are progress, main is truth](ADR-0102.md)); this panel
  is the history of the checkout the corpus serves.
- Without the git feature, or in a project that is not a repository, the panel
  says so and nothing else changes.

## Test plan

- [ ] a revision is attributed to the commit that introduced it, not the newest commit while it was current
- [ ] a status change that relocated the file is one revision with both paths, not a delete and an add
- [ ] the history endpoint returns subjects, authors, dates and status per revision
- [ ] the frontmatter diff reports a changed status, an added tag and a struck relation as three field changes
- [ ] an unchanged section is folded in the body diff; an edited one shows line hunks
- [ ] `opys diff <id>` with no revisions diffs the last commit against the working copy
- [ ] a non-repository project gets a notice, not an error

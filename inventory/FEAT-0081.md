# ID lease blocks in an orphan git ref

Layer 2 of [ADR-0055 — ID allocation: local lock, lease blocks in a ref, renumber as repair](ADR-0055.md)'s three-layer allocator, and the only one still unbuilt.
The advisory lock ([FEAT-0021 — Parallel-agent write safety](FEAT-0021.md)) serializes allocation on one machine; `renumber`
([FEAT-0017 — renumber: cross-branch ID collision repair](FEAT-0017.md)) repairs collisions after the fact. Between them sits the layer that
stops collisions happening across machines and branches in the first place —
and it needs nothing but the repository, which is why it belongs in the core
rather than in anything that has to be run for you.

A ledger of granted id blocks lives in an orphan ref, `opys/ids`, out of every
working tree. Taking a lease is commit-plus-push, and git's per-ref push
atomicity *is* the compare-and-swap: two claimants racing means one gets a
non-fast-forward rejection and retries against the next free block. Blocks are
sized by consumer — roughly ten for a person's node, a hundred for a busy one —
so the push round-trip is rare rather than per-document.

Unused ids inside a lease leave gaps in the sequence. Gaps are expected and
harmless: the invariant is monotonicity and never-reuse, not density. Do not
"fix" them.

## What has to happen first

**The allocation seam is not actually injectable yet.** `ids::IdSource` exists
and `SequenceMax` implements it, but `commands/new.rs`, `commands/query.rs` and
`commands/import.rs` each construct `SequenceMax` directly, and `ids.rs` says as
much in a comment: the construction moves behind `Ctx` when a second source
exists. That second source is this feature, so the move happens here. Until it
does, [FEAT-0021 — Parallel-agent write safety](FEAT-0021.md)'s claim that a lease source "replaces it without touching the
commands" is not true, and correcting that sentence is part of this work.

## The two problems that are not the happy path

**`refs/opys/*` is outside git's default fetch refspec.** A plain clone or a
fork does not bring the ledger. A node that then allocates sees an empty ledger,
leases block zero, and hands out ids another machine was already granted — the
exact failure this feature exists to prevent, arriving silently. Either the
fetch refspec is configured as part of adopting leases (and adoption has to say
so, loudly), or allocation refuses to lease when it cannot prove it read a
current ledger. The second is safer and should be the default; the first is the
convenience.

**Non-standard refs meet branch protection.** [ADR-0055 — ID allocation: local lock, lease blocks in a ref, renumber as repair](ADR-0055.md) says plainly: "Needs a
pushable non-standard ref; org branch-protection policies may need a carve-out —
document it." Nobody has. A team that cannot push `refs/opys/*` needs to know
before they adopt leases, not when the first push is rejected.

## Decisions this feature owns

- The ref name and the ledger's on-disk format. [ADR-0055 — ID allocation: local lock, lease blocks in a ref, renumber as repair](ADR-0055.md) wrote `opys/ids` as an
  example and later documents repeated it until it looked decided; it is not.
- Block sizing, and whether it is configurable per consumer or inferred.
- What happens on repeated non-fast-forward rejection — retry ceiling, backoff,
  and what the user is told when it gives up.
- Whether a lease expires. A node that takes a hundred ids and disappears leaves
  a hole; [ADR-0055 — ID allocation: local lock, lease blocks in a ref, renumber as repair](ADR-0055.md) says holes are fine, so the answer is probably "no, and that
  is deliberate" — but it should be written down rather than assumed.

## Test plan
- [ ] a lease is taken, persisted to the ref, and survives a fresh process
- [ ] two concurrent claimants: one wins, the loser retries and gets a disjoint block
- [ ] allocation from a lease never returns an id present in the ledger or the corpus
- [ ] a repository whose ledger ref was never fetched refuses to lease rather than allocating from empty
- [ ] gaps left by an unused lease do not trip `verify` and are not "repaired"
- [ ] `SequenceMax` remains the behaviour when no lease source is configured, byte-identically
- [ ] the commands allocate through `Ctx`, not by constructing a source directly

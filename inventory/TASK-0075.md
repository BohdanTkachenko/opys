# opys-server: systemd install, docs, and M1 closeout

The last mile: run the server as a service, document everything, and close
out [FEAT-0058 — opys-server: the always-on node](FEAT-0058.md).

Spec:

- `opys web install [--bind <ADDR>]`: write
  `~/.config/systemd/user/opys-server.service` —
  `ExecStart=<canonical path of the current executable> web start --bind
  <addr>`, `Restart=on-failure`, `[Install] WantedBy=default.target` — then
  print the `systemctl --user daemon-reload && systemctl --user enable --now
  opys-server` instructions (print, don't execute). Refuse to overwrite an
  existing unit unless `--force`. `uninstall` removes the unit file and
  prints the disable commands. On a non-systemd platform (no
  `$XDG_CONFIG_HOME`/systemd), print manual-run instructions and exit 0.
  Note in the docs that NixOS/home-manager users should declare the service
  instead (one-paragraph example in the README section).
- README.md: a new "The always-on node (`opys web`)" section — install, add a
  project, run, what the dashboard shows, the port, and the two guardrail
  sentences ("the API is typed; the node cannot execute arbitrary commands" and
  "the node serves only what you allowlisted"). Update AGENTS.md/CLAUDE.md
  likewise (brief). No AGPL note — [ADR-0076 — Apache for what runs on your machine; copyleft for the scaling layer](ADR-0076.md) made the whole workspace
  Apache-2.0.
- [FEAT-0058 — opys-server: the always-on node](FEAT-0058.md) closeout: check its Test plan items against the tests that now
  exist (reference real `mod::name` test names so the section check passes),
  fill its Manual verification procedure by actually running the server over
  this repo + one worktree, and set the feature's status accordingly
  (`implemented` if every test-plan item is covered, else `partial` with the

## Progress
- Filed as part of the M1 plan (see [FEAT-0058 — opys-server: the always-on node](FEAT-0058.md)'s Plan section).
- 2026-08-24: implemented. `opys web start|add|remove|list|scan|install|uninstall`
  now lives in the `opys` binary, which owns the top-level parser:
  `opys_engine::cli::Command` flattened in with `#[command(flatten)]` plus a
  `web` variant carrying `opys_server::cli::WebCommand`, each half dispatched to
  its own crate. **`opys-engine` still has no path to `opys-server`** — verified
  with `cargo tree`, since the engine is what every consumer embeds and it must
  not drag in axum or tokio. A unit test in `opys/src/main.rs` compares the
  duplicated root metadata (name, about, `--root`, `--no-sync`, the subcommand
  list) against `opys_engine::cli::Cli::command()`, because nothing else in the
  build would notice those drifting apart.
- `opys-server` lost `publish = false`, which ADR-0077 anticipated: a published
  crate cannot depend on an unpublished one, so linking it for `opys web` forces
  it public. All four crates now publish together in dependency order, and the
  stale release-plz comment about skipping one was rewritten.
- The 133 CLI integration tests passed **unmodified** through the restructure —
  confirmed by md5 against `HEAD`, not just by them being green.
- Closeout: six of the seven test-plan items were already covered by real tests.
  The seventh — "verify status matches `opys verify` exit semantics" — had the
  live half covered and the parity half covered by nothing, so rather than mark
  the feature `partial` I added `api::verify_agrees_with_the_cli_exit_code`,
  which runs the real CLI in-process against the same corpora the node serves.
  It pins clean → exit 0 / `ok` and problems → exit 1 / not `ok`, **and** the
  divergence: a config that will not parse is exit 2 for the CLI (an error, not
  a problem list) while the API answers `ok: false` like any other failure, with
  `load_error` as the only thing that tells them apart. FEAT-0058 is
  `implemented`, with that caveat written into its test plan rather than hidden.
- `opys.toml` needed one amendment for the closeout: the test-plan check's
  `roots` (and `[file_refs]`'s) were `src` + `opys/tests`, so a test plan citing
  a real test in the new crate could not resolve and the check would have pushed
  the author back to prose. Both now include `opys-server/src` and
  `opys-server/tests`.
- Adversarial review returned 23 findings, 9 major, all triaged. One honest
  nuance left in place: `opys web list` reports the bind address from the
  allowlist file, so starting the node with an explicit `--bind` makes `list`
  name a port nothing is listening on. That is the designed behavior — `list`
  never talks to a running node, which is the same rule that keeps paths out of
  the API — and the docs say so.
- End-to-end as a new user, in a fake `HOME` with two scratch projects: `list`
  on an empty allowlist explains itself, `scan` suggests without adding, `add`
  writes plain TOML with no node running, `start` serves the API and the UI, a
  second `add` is picked up **without a restart** (the first project's
  `loaded_at` untouched, same PID), an external file edit shows up in ~2 s,
  `remove` drops a corpus to 404 while the survivor keeps serving, and
  `{"action":"exec","cmd":"rm -rf /"}` is a 400 naming the six legal actions.

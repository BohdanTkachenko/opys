# opys-server: project discovery and the corpus registry

The node's data model, per [ADR-0077 — The node serves an explicit allowlist; discovery only suggests](ADR-0077.md): an explicit **allowlist** of what to serve,
the expansion of each entry into corpora, and a background scan that only ever
*suggests*. Nothing is served that the user did not allowlist. Two new modules,
`opys-server/src/registry.rs` and `opys-server/src/discover.rs`.

## The registry (`registry.rs`)

TOML at `$XDG_CONFIG_HOME/opys/server.toml`, falling back to
`~/.config/opys/server.toml`:

```toml
bind = "127.0.0.1:6797"        # optional; --bind overrides

[[project]]                    # serve exactly this project
path = "~/Projects/opys"

[[prefix]]                     # serve every project found under here
path = "~/work"
depth = 10                     # optional; default 10
```

- `load()` tolerates a missing file (empty allowlist, serve nothing) but not a
  malformed one — a parse error is a hard startup error naming the file and the
  line, because silently serving less than the user asked for is worse than
  refusing to start.
- `~` expands; every path canonicalizes on load. A path that does not exist is
  kept with an `error` note rather than dropped, so the UI can say "you
  allowlisted this and it is gone" instead of quietly forgetting it.
- `add(path)` / `remove(path)` rewrite the file preserving unrelated keys, and
  are idempotent. `add` on a directory containing `opys.toml` writes a
  `[[project]]`; `add --prefix` writes a `[[prefix]]`. Neither talks to a
  running node — the node watches this file ([ADR-0077 — The node serves an explicit allowlist; discovery only suggests](ADR-0077.md), so no endpoint ever takes
  a filesystem path).
- Unit-test round-tripping, `~` expansion, idempotent add/remove, the
  missing-file and malformed-file paths, all over a fake `$XDG_CONFIG_HOME`.

## Corpora (`discover.rs`)

Unchanged from the original plan — the types and the git rules are good:

```
Corpus { cid: String,            // stable id: sanitized canonical root + fnv64 hash,
                                 // same recipe as the backend's lock_path naming
         root: PathBuf,          // dir containing opys.toml (canonicalized)
         base: PathBuf,          // root joined with the config's base
         group: String,          // project-group key (see below)
         branch: Option<String>, // git branch checked out here, if a repo
         is_primary: bool }      // the main worktree of its group
ProjectGroup { key: String, name: String, corpora: Vec<Corpus> }
```

- Expanding the allowlist: a `[[project]]` entry contributes its own root; a
  `[[prefix]]` entry contributes every project the scan finds beneath it. Parse
  each config with `opys_engine::project_config::ProjectConfig::load` to resolve
  `base`; a root whose config fails to parse is kept with an `error` note (the
  API will show it) rather than dropped silently.
- Worktrees: for each corpus root, run `git -C <root> rev-parse
  --git-common-dir` (tolerate failure = not a repo). Roots sharing a
  canonicalized common dir form one `ProjectGroup`; additionally run `git -C
  <root> worktree list --porcelain` once per group and include any listed
  worktree that contains `opys.toml` at the same relative path as the group's
  primary, **even if it lies outside the allowlist** — approving a project
  approves its worktrees. The first entry of `worktree list` is the main
  worktree → `is_primary`. Branch comes from the porcelain output. Non-repo
  corpora form single-corpus groups keyed by their own path.
- Group `name` = last path component of the primary root. Group `key` = same
  hash recipe as `cid` over the common dir (or the root for non-repos).
- Shelling `git` is allowed here (the engine's `renumber` already shells git);
  every git call must tolerate absence of git or of a repo by degrading to a
  single-corpus group. Never fail discovery because git failed.

## The scan

One `walkdir`-based function, used for both prefix expansion and suggestions:

- Bounded to `depth` levels below the scan root (default 10). Skip hidden
  directories and this set by exact name: `node_modules`, `target`, `build`,
  `dist`, `out`, `vendor`, `third_party`, `__pycache__`, `venv`, `Pods`,
  `DerivedData`, `Binaries`, `Intermediate`, `Saved`. Do not follow symlinks;
  stay on one filesystem.
- Runs **in the background**, never on a request path and never blocking
  startup: at startup, on demand (`opys web scan` / the UI button), and on an
  hourly timer. Measured ~0.5 s over a 6.4M-entry `$HOME` at depth 10 with the
  skip list, so it is cheap only because it is rare — do not put it on the 60 s
  loop (see [ADR-0077 — The node serves an explicit allowlist; discovery only suggests](ADR-0077.md) for the full table).
- Suggestions are `{path, name, already_allowlisted: bool}` and are *never*
  auto-added. The default scan root is `~`.

## Progress
- Filed as part of the M1 plan (see [FEAT-0058 — opys-server: the always-on node](FEAT-0058.md)'s Plan section).
- 2026-08-23: spec rewritten against [ADR-0077 — The node serves an explicit allowlist; discovery only suggests](ADR-0077.md) (accepted). The original "walk the
  `run` command's argv roots and serve everything found" model is gone: the node
  serves an allowlist, discovery only suggests, and every walk is depth-bounded
  and backgrounded. The `Corpus`/`ProjectGroup` types and all the git worktree
  rules survive unchanged; what changed is where roots come from and that a scan
  can no longer put anything into service by itself.
- 2026-08-23: implemented. `registry.rs` is the allowlist (XDG path, `[[project]]`
  and `[[prefix]]` entries, `~` round-tripping both ways, idempotent add/remove
  that preserve unknown keys, missing file = empty vs malformed = hard error,
  vanished directories kept as error entries). `discover.rs` is the bounded
  `walkdir` scan plus allowlist expansion and git grouping, with `id_for` reusing
  the backend's lock-file hash recipe. 24 unit tests and 3 git integration tests,
  the latter skipping cleanly when git is absent. Deps added: `toml` and
  `walkdir`, both at the versions the engine already uses; `msrv` still builds on
  1.88.
- Two deliberate departures from the spec as written, both flagged rather than
  quietly absorbed:
  1. **The crate gained a `[lib]` target.** TASK-0067 defined it as a binary
     only, which predates [ADR-0077 — The node serves an explicit allowlist; discovery only suggests](ADR-0077.md) deciding that the CLI links this crate
     for `opys web` — a binary cannot be linked. Doing it now is a two-line
     manifest change; doing it after four more tasks have piled into `main.rs`
     would not be.
  2. **Branch labels survive a detached HEAD.** The spec says the branch comes
     from `worktree list --porcelain`, which reports `detached` for every
     jj-colocated repo — including this one, so the dogfood run showed a blank
     label on its own project. `worktree_list` now falls back to a branch
     pointing at HEAD, excluding branches checked out in sibling worktrees.
     A genuinely detached checkout still reports nothing. The union view
     ([TASK-0073 — opys-server: worktree union view](TASK-0073.md)) exists to label worktrees, so a permanently blank label
     would have undercut it.
- Worth knowing for whoever writes that fallback's neighbours: `git branch
  --points-at HEAD` emits a `(HEAD detached at abc1234)` pseudo-entry that sorts
  first and is not a branch name. `for-each-ref … refs/heads/` does not. The
  integration test caught it.
- Dogfooded on the maintainer's machine: `scan(~, 10)` finds 6 projects in
  ~520 ms (ADR-0077 predicted ~0.5 s), `expand` resolves this repo to one group
  with `base = inventory` and `branch = main`, and `suggest` marks the
  allowlisted one and offers the other five. Nothing was added to any allowlist
  without being asked.

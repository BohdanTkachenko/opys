# `opys log`: append a dated entry to a log section

Appending a line to a document's Progress log is the one body edit every agent
makes on every task, and today it is a hand edit: open the file, find the
section, add a bullet, hope the format matches. `opys log <id> "text"` makes it
a command. It finds the section the type declares with `kind = "log"`, appends a
bullet stamped with the UTC time, and runs the ordinary sync pass, so the
document's `updated` moves and the write goes through the inventory lock like
any other.

It exists for its own sake, and it is what the loop story leans on three times:
it is the heartbeat that says an agent is alive, the checkpoint the next stage
reads, and the way a harvester lands what it learned from an abandoned branch
onto main's copy of the task.

## Behaviour

- `opys log <id> "<text>"` appends `- <UTC timestamp> <text>` to the type's
  `log` section. `-` reads the text from stdin, for multi-line entries; the
  continuation lines are indented under the bullet.
- A type with no `log` section is an error (exit 2). A type with more than one
  needs `--section <heading>`.
- The splice is `body::apply_section_edits`, byte-accurate, so nothing outside
  the section changes. It is that function's only caller once `query --write`
  is gone ([ADR-0100 — SQL is read-only; every write is a lifecycle command](ADR-0100.md)).
- Entries are dated, so the `log` kind gains a meaning: verify checks that each
  bullet in a `log` section starts with an RFC3339 timestamp and that they do
  not go backwards. Existing undated bullets are reported, not rejected, until
  the migration document has been run.
- A rule can require it: `require_log_since_status = "Progress"` asserts that
  the named log section holds an entry stamped at or after the last `history`
  entry whose status *differs* from the one being guarded (the first key when
  every entry holds it), compared at whole seconds. That definition — not "the
  last history key" — is what makes the write-time check (which runs before the
  new key is appended) and the verify-time check agree, and it makes a
  `review → in-progress → review` bounce demand a fresh entry each time; see
  format.md's `require_log_since_status` for the worked example. The shipped
  config uses it on the transition into review, so a handoff without a
  checkpoint is refused.

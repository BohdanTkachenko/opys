# opys-server: corpus actor with warm store and watcher

The heart of the server: one **actor thread per corpus** owning a warm
`Store`, refreshed by file events. All store access is single-threaded by
construction — the store is **created inside the actor thread and never moved
across threads** (make no Send/Sync assumptions about it).

**The one rule that must not be broken** (spell it out in a comment): the warm
store is a read-only cache and must NOT retain the inventory lock. After every
load, immediately release it:

```rust
let (mut store, errors) = backend.load(&prj)?;   // takes the flock
drop(store.take_lock());                          // release it NOW
```

A warm store that keeps the lock deadlocks every CLI invocation against the
server (10 s timeout, then failure) — the regression test below pins this.

Spec:

- `opys-server/src/actor.rs`. Per corpus: `std::thread::spawn` a loop over an
  `std::sync::mpsc` channel of requests; each request carries a oneshot-style
  reply sender (`std::sync::mpsc::SyncSender` or tokio oneshot — bridge from
  async handlers with `tokio::task::spawn_blocking` or by using tokio
  channels' `blocking_recv` inside the thread; pick one and be consistent).
- Request enum (all replies are plain serde-able structs):
  - `Reload` → fresh `Project::open` + `backend.load` + release lock; then
    recompute and cache: doc summaries (id, type, status, title, tags, path,
    updated — via store SQL), verify problems
    (`verify::collect_problems(&prj, &docs, parse_errors)` over
    `store.all_docs()`), and `loaded_at` timestamp.
  - `Docs { type_, status, tag }` → filtered summaries from the cache.
  - `Doc { id }` → full doc: frontmatter fields, raw body, and `body_html`
    (comrak with default options — raw HTML stays escaped; do not enable
    `unsafe_`).
  - `Query { sql, params }` → `store.refresh_projections(&pcfg)` then
    `store.run_user_query(&sql, &params)`; return columns + rows or the error
    string. (Plan-guarded SELECT-only already enforced by the engine.)
  - `Verify` → cached problems + loaded_at.
  - `Shutdown`.
- Events: a `tokio::sync::broadcast::Sender<Event>` shared server-wide;
  the actor publishes `Event::CorpusReloaded { cid, docs, verify_problems,
  ts }` after every reload. (WS fan-out consumes this in [TASK-0071 — opys-server: read API and WebSocket events](TASK-0071.md).)
- Watcher: one `notify::recommended_watcher` per corpus watching `base`
  recursively plus the project's `opys.toml`. Raw events feed a debouncer in
  the actor: after an event, wait for a 250 ms quiet period (drain further
  events) before reloading, so a burst (e.g. `opys sync` rewriting 40 files)
  causes one reload. Ignore events for the backend's lock file and for
  non-`.md`/non-`opys.toml` paths.
- Corpus add/remove, split by cost per [ADR-0077 — The node serves an explicit allowlist; discovery only suggests](ADR-0077.md): every 60 s (tokio interval in
  the main loop) re-check only what is already known — stat each served root and
  its `opys.toml` — and additionally react to the registry file changing. The
  deep scan that *finds* new projects under a prefix entry is the background
  job's hourly pass, not this loop. Either way: spawn actors for new corpora,
  send `Shutdown` to removed ones, publish
  `Event::CorpusAdded`/`CorpusRemoved`.
- Tests (fixture corpora = tempdir with opys.toml + doc files, engine-style):
  - `reload_releases_the_inventory_lock`: after the actor loads, a plain
    `MarkdownLocal.load(&prj)` from the test thread succeeds within 2 s
    (`OPYS_LOCK_TIMEOUT_MS=2000`). **This is the deadlock regression test.**
  - `docs_and_doc_and_query_answer_from_the_warm_store`.
  - `external_edit_triggers_debounced_reload`: write a doc file directly, wait
    ≤2 s, cache reflects it and exactly one reload event was broadcast.
  - `verify_problems_are_cached_and_refreshed`.

## Progress
- Filed as part of the M1 plan (see [FEAT-0058 — opys-server: the always-on node](FEAT-0058.md)'s Plan section).
- 2026-08-23: implemented as `opys-server/src/actor.rs` (one thread per corpus
  owning the warm store, the request enum with sync reply channels, the notify
  watcher and the 250 ms quiet-period debounce) and `opys-server/src/manager.rs`
  (the live actor set). The lock discipline is in place and pinned:
  `reload_releases_the_inventory_lock` takes a CLI-style
  `MarkdownLocal.load` from the test thread while the actor is warm and fails if
  it takes longer than 1.5 s with `OPYS_LOCK_TIMEOUT_MS=2000`.
- **Found and fixed a bug that would have shipped invisibly: the corpus reloaded
  itself in a permanent loop.** inotify reports *reads* — opening a file emits
  `Access(Open)` — and a load opens every document in the corpus. The first
  filter looked only at path names, so every load re-triggered itself: one core
  pinned per corpus, forever, with every functional test still passing. The
  debounce test noticed a second reload it did not ask for; the follow-up test
  `a_quiet_corpus_does_not_reload_itself` proved an untouched corpus reloads
  anyway. `is_change` now rejects `EventKind::Access(_)` before looking at paths,
  with `reads_are_not_changes` covering the classification directly.
- Two interpretation calls worth naming:
  1. `Event::CorpusReloaded` carries *counts* (`docs`, `verify_problems`), not
     the documents themselves. A broadcast channel clones per receiver and
     buffers for slow ones, so pushing whole corpora through it would cost
     memory proportional to viewers times corpus size for data most subscribers
     already hold. [TASK-0071 — opys-server: read API and WebSocket events](TASK-0071.md) can fan out richer payloads if the UI wants
     them without changing this.
  2. A load that fails leaves the previous warm state answering reads and
     records why in `VerifyStatus::load_error`, rather than emptying the corpus.
     A project whose `opys.toml` is mid-edit stays readable and says it is stale.
- **Not done here, by design:** nothing drives `Manager::refresh`/`rescan` yet.
  The spec's "tokio interval in the main loop" needs a main loop, and `main.rs`
  still serves only `/api/health` — the interval belongs with the server in
  [TASK-0071 — opys-server: read API and WebSocket events](TASK-0071.md). Both passes exist as tested primitives: `refresh` is the
  cheap tick (stat what is served, react to the registry file, which is also
  watched) and `rescan` is the expensive one, exactly the split [ADR-0077 — The node serves an explicit allowlist; discovery only suggests](ADR-0077.md)
  requires.
- Tests: 23 unit, 7 actor integration, 5 manager integration, 3 git — full CI
  gate and `msrv` green, no new dependencies.
- Dogfooded over this repo's own inventory: warm in 42 ms for 56 documents,
  `docs()` from cache in 62 µs, a `GROUP BY` query in 4.2 ms, `verify` clean and
  matching the CLI. With the actor warm, a real `opys list --type adr` completed
  in 17.5 ms and exited 0 — the lock guarantee holding outside the test harness,
  which is FEAT-0058's "a warm server never blocks a concurrent CLI invocation"
  test-plan item.

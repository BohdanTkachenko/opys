# The node walks the filesystem before it binds its socket

[ADR-0077 — The node serves an explicit allowlist; discovery only suggests](ADR-0077.md) is explicit that suggestion scanning "runs as a **background job** —
never on a request path, **never blocking startup**", and `discover::scan`'s own
doc comment repeats it: "Never call this on a request path or at startup's
critical path."

The shipped node does exactly that. `opys-server/src/serve.rs` calls
`rescan_and_report` at line 110, before `TcpListener::bind` at line 127 —
so the startup rescan expands the allowlist first, and for a `[[prefix]]` entry
that means `discover::scan`'s bounded walk. The function forbids what its own
caller does.

The cost is startup latency, not correctness: ~0.5 s warm over a large home
directory and materially worse cold, during which the HTTP surface does not
exist at all. A user with a prefix entry gets a node that refuses connections
for as long as the walk takes, which is precisely the shape [ADR-0077 — The node serves an explicit allowlist; discovery only suggests](ADR-0077.md) refused.

The fix is small — bind and serve first, then kick the initial rescan onto the
blocking pool the periodic passes already use — but it needs care about what a
request sees in the window before the first rescan finishes. An empty
`/api/projects` that later fills in is honest; a 500 is not. Deciding that, and
saying so in the response, is most of the work.

## Reproduction

1. Put a `[[prefix]]` entry covering a large directory in the allowlist, e.g.
   `path = "~"` at the default depth.
2. Drop the filesystem caches so the walk is cold (needs root), or use a
   directory tree large enough that the warm walk is still seconds.
3. Run `opys web start` and immediately `curl` the bind address in a loop.

Connections are refused until the walk completes; the listening line on stderr
does not appear until then either.

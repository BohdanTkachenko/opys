# Manage opys.toml from the web UI

Everything today is driven by `opys.toml`, and editing it is the steepest part
of getting started: TOML, a schema you have to learn from the format spec, and
no feedback until the next `verify`. The web UI should carry a config view —
see the current types, statuses, sections and rules; add a status to a type;
add a tag-required flag; create a new type from a template — with the node
validating through the engine's own `ProjectConfig::validate` before anything
is written, and refusing edits that would orphan existing documents (removing a
status documents still hold, deleting a type with live ids).

Two constraints shape the design. The request vocabulary must stay typed and
closed ([ADR-0077 — The node serves an explicit allowlist; discovery only suggests](ADR-0077.md)) — structured config mutations, never "write this file". And
the file on disk stays the single source of truth, hand-editable, with the UI
as a second hand on it — same philosophy as every other write. Config edits are
corpus-wide in effect, so the first cut should probably be read-only display
plus the narrowest safe mutations (add a status, add a type from template)
rather than a general editor.

- [ ] a mutation that would orphan documents is refused, naming them

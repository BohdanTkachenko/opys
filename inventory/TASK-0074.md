# opys-server: embedded web UI

The human surface ([ADR-0050 — Retire the TUI; the web UI over the server is the human surface](ADR-0050.md)). Decided approach — **no build pipeline**: plain
HTML + vanilla ES modules + one stylesheet, living in `opys-server/ui/`
(`index.html`, `app.js`, small per-view modules if helpful, `style.css`),
embedded into the binary with `include_str!`/`include_bytes!` and served by
axum (`GET /` and `GET /ui/*` with correct content-types). **Zero external
requests** — no CDN scripts, no webfonts; the page must work offline. No
framework, no npm, no bundler; if it needs a compile step, it's out of scope.

Views (client-side hash routing, e.g. `#/corpus/<cid>/doc/<id>`):

1. **Sidebar**: project groups → corpora (branch label, primary marker), from
   `GET /api/projects`; a red/green verify dot per corpus; auto-refreshes on
   WS events.
2. **Board** (default per corpus): docs grouped into columns by status,
   filter controls for type/tag/text; click-through to the doc view. Data
   from `/docs`.
3. **Doc view**: `body_html` rendered (it is pre-escaped by the server),
   frontmatter chips (status, tags, relations as links), and the action bar:
   status picker (populated from the *type's* statuses minus terminal ones —
   fetch the doc, derive from the config-provided list the API includes),
   tag add/remove, block/unblock by id, close (with confirm dialog noting it
   deletes the file). Actions POST to `/action`; a 422 shows the error
   message inline verbatim.
4. **Query console**: textarea + run button → `/query`, rendered as a table;
   errors shown verbatim; a few canned example queries as buttons.
5. **Union view** per group: the `/union` table — columns per corpus, drifted
   rows highlighted, collision rows marked strongly.
6. **Live**: subscribe to `/api/events`; on `corpus-reloaded`/`action-completed`
   refresh whatever view is active; show a small "reconnecting…" state when
   the WS drops (retry with backoff).

Note for the doc view's status picker: extend the `GET /doc` payload in
`api.rs` with `allowed_statuses` (the type's non-terminal statuses) rather
than teaching the UI about opys.toml — one server-side line, keeps the UI
dumb.

Styling: minimal, readable, dark-mode via `prefers-color-scheme`. No
pixel-perfection — this UI will be iterated after M1; correctness and
robustness first.

Testing: server-side only — assets are served with the right content-types
and non-empty bodies (oneshot tests); the API contract the UI consumes is
already covered by [TASK-0071 — opys-server: read API and WebSocket events](TASK-0071.md)/72/73 tests. Interactive behavior is verified via
the Manual verification section of [FEAT-0058 — opys-server: the always-on node](FEAT-0058.md) at closeout ([TASK-0075 — opys-server: systemd install, docs, and M1 closeout](TASK-0075.md)).

# Scan modes and first-run onboarding

Discovery works and finds everything; it just never acts. A first-time user
starts the node, opens the dashboard, sees one project or none, and has no way
from the browser to learn that `opys web scan` would have found five — or to do
anything about it if they did. The fix is to make the *policy* configurable
instead of hardcoded, and to ask the user for that policy once, in the UI, at the
moment they first arrive.

## Scan modes

A single `mode` in `server.toml` decides what the periodic scan does with what it
finds:

- **`off`** — no scanning. For a large `$HOME`, or a user who wants the
  allowlist to be exactly what they wrote.
- **`suggest`** — scan, and surface the results as accept/ignore suggestions in
  the UI. Nothing is served until accepted. This is today's behavior, and the
  default for an existing config that predates the setting.

The modes differ only in what happens after the walk, so `scan` stays one code
path and the CLI's `opys web scan` remains its `suggest` face.

**A suggestion is a path and nothing more.** It must never be a loaded corpus: no
document count, no verify dot, no title preview beside an unaccepted entry.
Rendering any of those means opening the project first, and opening a project
means reading whatever its `opys.toml` points `base` at ([BUG-0084 — A project's inventory base can escape its root](BUG-0084.md)) — which is
precisely the read this mode exists to keep behind a human. The suggestion list
shows the directory it found and waits.

There is deliberately **no auto-add mode.** It was drafted and cut. What it buys
is one click, now that suggestions live in the UI rather than behind an SSH
session; what it costs is the explicit-allowlist property that is the whole point
of [ADR-0077 — The node serves an explicit allowlist; discovery only suggests](ADR-0077.md). A directory allowlisted with nobody in the loop is loaded
with nobody in the loop, and loading is already the sensitive step. The trade is
bad in both directions, so the human stays.

## Onboarding

When the node starts with **no config file at all** — distinct from an empty or
mode-`off` one, which are decisions already made — the dashboard opens on a
one-screen setup instead of an empty board: pick a mode, pick a scan root, see
what that combination would find right now, confirm.

The root defaults to `~/Projects` when it exists and `$HOME` otherwise — a
narrower root is a shorter walk and a shorter suggestion list, and the user can
widen it in the same screen.

Completing onboarding writes `server.toml`; choosing a mode is what writes it.
There is no separate "skip", because the screen *is* what a node serving nothing
shows — there is nothing to skip past, and a dismissed empty dashboard would be
worse than the screen that explains it. Once entries exist the board takes over
and this becomes the allowlist panel, reachable at `#/setup`.

## Adding projects from the UI

Per [ADR-0082 — The web UI may manage the allowlist within $HOME](ADR-0082.md), the UI can allowlist a discovered project *and* a
directory the user types. Both go through one validator:

1. canonicalize (resolving `..` and symlinks),
2. require the result under the canonicalized `$HOME`,
3. reject any component beginning with `.` — reusing `discover::is_skipped`, so
   the UI and the scan cannot disagree about what is hidden.

Order matters: validating the spelling before canonicalizing accepts
`~/Projects/link-to-etc`. Anything outside `$HOME` stays editable in
`server.toml` only.

## What has to happen first

**[BUG-0079 — The node walks the filesystem before it binds its socket](BUG-0079.md) blocks a `$HOME` default root.** The startup rescan runs before
`TcpListener::bind`, so a wide root means the dashboard is unreachable for the
length of the walk — the shape [ADR-0077 — The node serves an explicit allowlist; discovery only suggests](ADR-0077.md) refused. Cheap warm (~27 ms over
this machine's `$HOME`), materially worse cold, and onboarding is exactly the
first-run, cold-cache moment.

[BUG-0084 — A project's inventory base can escape its root](BUG-0084.md) does **not** gate this feature, now that auto-add is out. A
human sees the path before anything is opened, so an escaping `base` cannot be
reached without someone accepting the project that carries it. It has since been fixed
anyway — an accepted project should not read or write outside its own root
either — but it was never a prerequisite for this.

## Manual verification

### Setup
- A build of the node and a fake `$HOME` with no `~/.config/opys/server.toml`.
- Two projects under `<fake-home>/Projects`, one directory outside `$HOME`, and
  a symlink inside `$HOME` pointing outside it.

### Procedure
1. Start the node and open the dashboard.
2. Choose `suggest`, accept the default root, confirm; check `server.toml`.
3. Add one discovered project from the UI, then a typed path to the other.
4. Type the outside-`$HOME` path, then the symlink, then a dot-path.
5. Stop the node, add an outside-`$HOME` entry to `server.toml` by hand, restart.
6. Create a third project under the root; accept one suggestion and ignore another.
7. Restart the node with the config now present.

### Expectations
- Step 1 shows onboarding, not an empty board; step 2 writes a config naming the
  chosen mode and root.
- Step 3 serves both projects, and the typed one is indistinguishable from the
  discovered one in the resulting file.
- Step 4 rejects all three with a message naming the rule, and writes nothing.
- Step 5's hand-added entry is served untouched — the UI's rules bind the UI, not
  the file.
- Step 6 suggests the new project without opening it, serves the accepted one
  immediately, and does not re-suggest the ignored one.
- Step 7 goes straight to the board; onboarding does not reappear.

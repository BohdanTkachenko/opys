# Files and git are the only truth; the server is a view

## Context

Introducing an always-on server ([FEAT-0058 — opys-server: the always-on node](FEAT-0058.md))
creates pressure to move authoritative state into the long-lived process or a
real database: sub-second propagation, no merge latency, ACLs. But the
product's differentiators all flow from repo-as-database: task state versioned
with the code (`implemented` can only mean *merged* — a server-side DB happily
records it for code that never landed), offline operation, greppability,
agent-nativeness, spec review via PR, and zero required infrastructure
([FEAT-0043 — Centralized global ID allocation](FEAT-0043.md)'s wontfix: "no host, no accounts, works offline"). In-VCS tracking
is proven at team scale — SQLite has run its bug tracker inside Fossil for
nearly two decades; git-bug and git-appraise are the same idea on git.

opys already works as materialized-view-over-files *per invocation*: load
markdown → in-memory SQL store → mutate → flush. `sync` + `verify` already are
the recovery path for hand edits.

## Decision

Markdown files in git remain the sole authoritative store at every scale —
solo, fleet, and team. The server is that existing store lifecycle held open:
a warm, watcher-refreshed cache serving reads, never a second source of truth.
Divergence (branches, worktrees, per-node uncommitted state) is *presented* as
labeled overlays in a union view, never resolved by the server — git merge
remains the only merger. Server-mediated writes are the same local engine
writes (command cores + flush + advisory lock) triggered remotely, and the CLI
must work forever with no server running. A database `Backend` implementation
(the trait exists for this) stays a documented escape hatch, not a roadmap
item: the moment truth leaves the repo, opys competes with Linear/Jira/GitHub
Issues on their turf instead of being what they structurally cannot be.

## Consequences

- The server needs no consistency machinery: reload-on-change (~100 ms for a
  1,400-doc corpus) and the flush plan already define its read and write paths.
- Merge latency is addressed by view-layer liveness (the union view and node
  mesh), not by changing storage semantics.
- Registry history stays entangled with code history (reverts revert task
  state). Accepted: it is the honest semantics for code-describing statuses;
  the fast path for main-tracked edits is a policy question for whatever
  coordinates the mesh.
- Cross-repo programs get view-level federation (the server is multi-project)
  before any storage-level cross-repo relations.

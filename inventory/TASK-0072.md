# opys-server: action endpoint through the command cores

Writes. The server is a *remote hand on the local write path*, never a second
write authority ([ADR-0051 — Files and git are the only truth; the server is a view](ADR-0051.md)): every action performs a **fresh, CLI-identical
cycle** — `Project::open` → `backend.load` (which takes the [FEAT-0021 — Parallel-agent write safety](FEAT-0021.md) lock) →
engine `core()` → `sync::pass` → `backend.flush` — inside
`tokio::task::spawn_blocking`. **Never write through the warm store**: it was
loaded in the past without holding the lock, so flushing it would clobber CLI
writes made since. The warm store then refreshes itself via the watcher like
after any external write.

Route: `POST /api/corpus/{cid}/action`, body is a tagged enum
(`#[serde(tag = "action", deny_unknown_fields)]` — an unknown action or extra
field is a 400 at deserialization, which is the no-arbitrary-execution
guardrail, plus a test pinning it):

```
{"action":"new",        "type": "...", "title": "...", "tags": "a,b", "status"?: , "features"?: , "reason"?: }
{"action":"set-status", "id": "...", "status": "...", "reason"?: }
{"action":"tag",        "id": "...", "add"?: "a,b", "remove"?: "c"}
{"action":"block",      "id": "...", "by": "..."}
{"action":"unblock",    "id": "...", "by": "..."}
{"action":"close",      "id": "...", "force"?: bool}
```

Mapping (all six cores already exist — see Progress): `new::core`, `set_status::core`,
`tag::core`, `block::block_core`, `block::unblock_core`, `close::core`. After
the core, run the same auto-sync pass the CLI runs (mirror what
`commands::maybe_sync`/`sync` do — reuse `sync::pass` + flush; read those fns
and reproduce the call sequence, do not reinvent the logic), then reply
`{ok: true, id, message}` or map the `OpysError` to
`{error: "<display>"}` with status 422 (the CLI's exit-2 class). On success,
broadcast `Event::ActionCompleted { cid, action, id }`.

Tests (fixture corpora; run the server pieces in-process):

- each action end-to-end: file changed on disk exactly as the CLI would
  change it (compare against running the same engine core directly);
- `unknown_action_is_rejected` (400, nothing on disk changes);
- `invalid_transition_is_a_422` (e.g. set-status to a terminal status —
  message matches the CLI's);
- `action_and_cli_interleave_safely`: with a warm actor running, perform a
  server action and a direct `backend`-level write back-to-back; both
  succeed (the lock serializes them; no deadlock, no lost write);
- `close_broadcasts_and_cache_catches_up`: after close, the doc disappears
  from `Docs` within the debounce window.

## Progress
- Filed as part of the M1 plan (see [FEAT-0058 — opys-server: the always-on node](FEAT-0058.md)'s Plan section).
- 2026-08-23: this task's premise is verified and needs no engine work first.
  TASK-0068 was filed to extract print-free `block_core`/`unblock_core` and
  closed as a no-op: they already existed (`src/commands/block.rs:19` and `:76`,
  from commit cf3f0e9 on 2026-06-16, when the TUI needed them). An audit across
  every mutating command module confirms all six cores this endpoint calls are
  print-free — `new::core`, `set_status::core`, `tag::core`, `close::core`,
  `block::block_core`, `block::unblock_core` — and that every `println!` in
  `src/commands/` sits in a `run`-style wrapper. The only other output is
  `eprintln!` in the shared `for_each_id` and `maybe_sync` helpers, both
  wrapper-level and unreachable from a core. Nothing the node calls can write to
  its stdout.
- 2026-08-24: implemented in `opys-server/src/action.rs` (the closed action
  vocabulary and the write cycle) plus the route in `api.rs`. Every action is a
  fresh `Project::open` → `backend.load` (flock) → core → `flush` →
  `sync::run` cycle on the blocking pool; the warm store is never written
  through, and catches up via its watcher like it would after any external edit.
  `Event::ActionCompleted` rides the existing tag, so the WebSocket forwards it
  as `action-completed` with no special-casing.
- **The review found an allowlist escape on the write path, and it is the most
  important thing in this task.** `Project::open` searches *upward* for
  `opys.toml` — the CLI's convenience. So a corpus whose own config had gone (a
  branch switch, a removed worktree, a rename) still resolved for up to a minute,
  until `Manager::refresh`'s next tick, and the write cycle would land in the
  nearest *enclosing* project — one the user never allowlisted — answering
  200 OK. Nested projects are the normal shape a `[[prefix]]` entry produces, so
  this was not exotic; it drove a hole straight through ADR-0077's only security
  boundary. Two independent review lenses found it and demonstrated it with a
  throwaway test. `perform` now refuses before opening, using the exact predicate
  `Manager::refresh` uses to call a corpus gone, with a second canonical-prefix
  check behind it and a regression test.
- Adversarial review returned 16 findings, 6 major, all triaged and the real ones
  fixed. Beyond the escape above, the useful ones were about error semantics: a
  write the node could not attempt because another writer held the lock now
  answers **503** (retry) rather than 422 (your write is invalid) — a distinction
  the spec did not draw but a client needs, since 404 means stop, 503 means try
  again, and 422 means show the user. Its test lives in its own binary because
  `OPYS_LOCK_TIMEOUT_MS` is process-global and this test needs a short one while
  the main action suite needs a generous one.
- **Byte-identity with the CLI was proved, not asserted.** Two fresh copies of a
  corpus, the same six-step sequence run through HTTP against one and through
  `target/debug/opys` against the other, then `diff -r`: empty. Not one byte
  differs, `created`/`updated` included. That is the FEAT-0058 "remote hand on
  the local write path" guarantee demonstrated on disk.
- Dogfooded over a scratch copy (never the real inventory): all six actions over
  real HTTP, each reply's `message` matching the CLI's own line; the closed
  vocabulary rejecting `{"action":"exec","cmd":"rm -rf /"}` with 400 *unknown
  variant* and a smuggled `"path":"/etc/passwd"` with 400 *unknown field*, both
  before any work; three 422s (terminal status, unknown status, unknown id) that
  left the target file byte-for-byte unchanged; and a WebSocket client receiving
  exactly seven `action-completed` frames — one per successful write, none for a
  refused one. A `GET` issued straight after each 200 already reflected the
  write, so the endpoint is read-your-own-write without waiting on the watcher.
- Tests: 16 in `tests/actions.rs`, 1 in `tests/action_busy.rs`, plus additions to
  the actor and api suites. `opys/tests/cli.rs` — the byte-identity pin — is
  untouched, and no engine file was modified. Full CI gate and `msrv` green.

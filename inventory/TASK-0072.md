# opys-server: action endpoint through the command cores

Writes. The server is a *remote hand on the local write path*, never a second
write authority ([ADR-0051 — Files and git are the only truth; the server is a view](ADR-0051.md)): every action performs a **fresh, CLI-identical
cycle** — `Project::open` → `backend.load` (which takes the [FEAT-0021 — Parallel-agent write safety](FEAT-0021.md) lock) →
engine `core()` → `sync::pass` → `backend.flush` — inside
`tokio::task::spawn_blocking`. **Never write through the warm store**: it was
loaded in the past without holding the lock, so flushing it would clobber CLI
writes made since. The warm store then refreshes itself via the watcher like
after any external write.

Route: `POST /api/corpus/{cid}/action`, body is a tagged enum
(`#[serde(tag = "action", deny_unknown_fields)]` — an unknown action or extra
field is a 400 at deserialization, which is the no-arbitrary-execution
guardrail, plus a test pinning it):

```
{"action":"new",        "type": "...", "title": "...", "tags": "a,b", "status"?: , "features"?: , "reason"?: }
{"action":"set-status", "id": "...", "status": "...", "reason"?: }
{"action":"tag",        "id": "...", "add"?: "a,b", "remove"?: "c"}
{"action":"block",      "id": "...", "by": "..."}
{"action":"unblock",    "id": "...", "by": "..."}
{"action":"close",      "id": "...", "force"?: bool}
```

Mapping (all six cores already exist — see Progress): `new::core`, `set_status::core`,
`tag::core`, `block::block_core`, `block::unblock_core`, `close::core`. After
the core, run the same auto-sync pass the CLI runs (mirror what
`commands::maybe_sync`/`sync` do — reuse `sync::pass` + flush; read those fns
and reproduce the call sequence, do not reinvent the logic), then reply
`{ok: true, id, message}` or map the `OpysError` to
`{error: "<display>"}` with status 422 (the CLI's exit-2 class). On success,
broadcast `Event::ActionCompleted { cid, action, id }`.

Tests (fixture corpora; run the server pieces in-process):

- each action end-to-end: file changed on disk exactly as the CLI would
  change it (compare against running the same engine core directly);
- `unknown_action_is_rejected` (400, nothing on disk changes);
- `invalid_transition_is_a_422` (e.g. set-status to a terminal status —
  message matches the CLI's);
- `action_and_cli_interleave_safely`: with a warm actor running, perform a
  server action and a direct `backend`-level write back-to-back; both
  succeed (the lock serializes them; no deadlock, no lost write);
- `close_broadcasts_and_cache_catches_up`: after close, the doc disappears
  from `Docs` within the debounce window.

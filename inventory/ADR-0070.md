# Declared work branches carry a document through its stages; main stays the truth for completion

## Context

One project already runs its whole pipeline as status queues ([ADR-0068 — Statuses are owned by declared roles; a role is only a name](ADR-0068.md)):
a task is planned, researched, condensed into a fact sheet, written up as a
spec, reviewed, signed off by a person, implemented, reviewed again and landed,
each step by whichever agent owns that status. Running it showed three costs of
keeping all of it on main:

- **Two statuses per step.** A queue status (`to-research`) and a working
  status (`researching`) exist only so that a claim is visible and atomic. The
  graph doubles, every owner map and ttl table doubles, and the person reading
  it has to know which half is "waiting".
- **Main fills with in-between work.** Every claim and every step is a commit
  on main, and the scaffolding of a spec (the planner's brief, the research
  answers, the fact sheet) lands in the finished inventory.
- **The product is not the step.** The spec is split into steps because agents
  do each step better, but what the person signs off is one spec. Nothing
  ties the steps together as one unit of work under review.

The project's owner wants one status per stage, a claim visible some other
way, and one branch per unit of work: a **spec branch** whose steps end in a
reviewable spec, and an **implementation branch** for that spec's code.

Two accepted decisions stand in the way. [ADR-0053 — Branches are progress, main is truth](ADR-0053.md) decision 1
makes main the only truth for pickability, so a document that main still
holds at `todo` can never be picked at `research` on its branch.
[ADR-0027 — Files and git are the only truth; the server is a view](ADR-0027.md) keeps opys out of merging and out of any forge, which
this decision keeps.

## Decision

1. **A type may declare work branches.** Each declaration names a ref template
   (`spec/{id}`), the status on main it starts from (`todo`), the **stages**
   that happen on the branch (`plan`, `research`, `condense`, `write`,
   `spec-review`, `spec-approval`, `needs-human`), and the status main shows
   once the branch is merged (`ready`). A second declaration covers the
   implementation (`impl/{id}`: `implement`, `review`, `land`; merged:
   `done`). A type without declarations behaves exactly as today.
   A stage may belong to several declared branches.
2. **Inside its declared stages, a document's work branch is the truth.**
   `next`, `queue`, `list --status` and the node read a document at a stage
   from its work branch: the branch copy is the one that is pickable, owned
   and shown. Main's copy, still at the starting status, is reported as
   occupied by that branch, never as pickable. Only declared refs count, read
   through the existing ref reader ([FEAT-0058 — Branch reader: the in-binary git adapter](FEAT-0058.md)); an arbitrary
   branch stays progress only, as [ADR-0053 — Branches are progress, main is truth](ADR-0053.md) says.
3. **Main stays the truth for everything else.** Completion, blocker release,
   terminal statuses, `close` and `retire` happen on main only. Nothing is
   finished until the branch is merged. This narrows
   [ADR-0053 — Branches are progress, main is truth](ADR-0053.md) decision 1; it does not reverse it.
4. **One status per stage; a claim is a field, not a status.** A type may
   declare a claim field (`claimed_by`) and a claim ttl. A branch copy with the
   field set is in progress: `next` leaves it out, `queue` and the node show
   who holds it and since when, and `verify` reports a claim older than its
   ttl. How a claim is taken atomically (for example a fast-forward-only push
   of the claiming commit) is the orchestrator's, not opys's.
5. **Merging, pushing and forges stay outside opys** ([ADR-0027 — Files and git are the only truth; the server is a view](ADR-0027.md)).
   An orchestrator opens a pull request if it wants one, moves the document to
   its human-review stage, merges when the person approves, and folds or drops
   scaffolding as the project chooses. opys sees only the statuses. Which
   approval style a project uses (a person's status change, or a pull request
   the orchestrator watches) is the orchestrator's configuration; to opys both
   are the same human-review stage owned by a person.
6. **`verify` guards the shape.** It reports a document with two open work
   branches of the same kind, a branch copy at a status that is not one of its
   declared stages, a main copy that left its starting status while its branch
   is open, and a merged branch whose main status is not the declared one.
   Two branches of different kinds open at once are reported and make the
   document unavailable.

## Consequences

- `next` and `queue` open git for types that declare work branches. Until now
  `next` never opened git ([FEAT-0057 — `opys next`: the pick oracle](FEAT-0057.md)); a project without
  declarations, or without a repository, keeps that behaviour, and a build
  without the `git` feature refuses a declaration at config load rather than
  silently ignoring it.
- What opys reports is only as fresh as the refs it can read. Remote branches
  need the existing opt-in `branches` patterns and an orchestrator that keeps
  them fetched; a stale fetch shows stale stages.
- A person who edits a document on main while its branch is open creates a
  conflict for the orchestrator's merge. The node should steer edits of a
  branch-held document to its branch copy; `verify` reports main drifting.
- The transition graph is checked on the branch copy as it is on main, so the
  stage graph is declared once, in the type's `[transitions]`.
- History stays per copy: the branch carries the stage timeline, and the merge
  brings it to main, so `opys history` after the merge shows every stage.

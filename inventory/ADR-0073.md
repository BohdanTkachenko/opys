# An opt-in dispatcher runs the queues inside the node; files and git stay the only truth

## Context

opys has kept orchestration out from the start. The README says that driving
agents around the inventory belongs to an orchestrator that uses opys as its
tracker, and that opys starts no write off its own clock. [ADR-0027 — Files and git are the only truth; the server is a view](ADR-0027.md) keeps the
node a view. Between them, [ADR-0053 — Branches are progress, main is truth](ADR-0053.md)'s scope note, [FEAT-0057 — `opys next`: the pick oracle](FEAT-0057.md), [ADR-0068 — Statuses are owned by declared roles; a role is only a name](ADR-0068.md)
decision 8 and [ADR-0070 — Declared work branches carry a document through its stages; main stays the truth for completion](ADR-0070.md) decisions 4 and 5 leave claims, leases, liveness,
merging and agent runs to that orchestrator. It was to be kobzar: a separate
product driving opys through the node's HTTP/WebSocket API, with adapters for
other trackers later.

kobzar was never built. Two projects run quick, project-specific dispatchers
instead. They were written fast and are not a design to copy, but they show
what a dispatcher needs and where the planned split did not hold:

- **They drive opys through its CLI and git, not the node's API.** They pick
  with `opys next`, claim with `opys apply`, check with `opys verify` and route
  by the `owners` map. The roles, claim fields and work branches of [ADR-0068 — Statuses are owned by declared roles; a role is only a name](ADR-0068.md)
  and [ADR-0070 — Declared work branches carry a document through its stages; main stays the truth for completion](ADR-0070.md) were written for one of them. Neither talks to another tracker.
- **What they add is git and process work.** A worktree per work branch, a
  claim made atomic by a fast-forward-only push, a sandboxed agent run per
  stage, provider quota checks, notifications, a person's sign-off, the merge
  to main, and a gate before landing.
- **They are one program, copied.** The second is a near-verbatim copy of the
  first, and the copies already drift. What differs between them, and what
  would differ for a third project, falls into two groups: project settings
  (the types and stages dispatched, the prompt and model per stage, the
  approval style per type, the gate command) and machine settings (worker
  counts and quota thresholds, which differ today because both projects share
  one machine's provider quota).
- **They leave gaps a person fills by hand.** An expired claim stays until
  someone runs a reclaim command, and an item waits at landing until someone
  lands it. `verify` reports the first and, by design, fixes neither.

Nobody wants the dispatcher without opys, and a dispatcher for some other
tracker is not a product anyone has asked for. Kept apart, the two cost two
releases, a second long-running process watching the same files, and a write
API the node does not have: it would have to commit, push, write to branches
that are not checked out, and authenticate its writers, all for one client.

The options:

1. **kobzar as planned**, a separate program over the node's API. It needs
   everything in the last paragraph.
2. **kobzar linking `opys-engine`.** No remote API, but two daemons per
   project on the same files, two web UIs and two configs.
3. **The scripts grown into an `opys dispatch` command run by a timer.** Close
   to what runs today, but the web UI cannot see sessions or budgets, and every
   tick reloads a corpus the node already holds.
4. **A dispatcher inside the node, off unless configured.** Chosen.

## Decision

1. **opys ships a dispatcher, and the node runs it.** It is a workspace crate,
   `opys-dispatch`, that depends on `opys-engine`; the engine never depends on
   it, just as it never depends on `opys-server`. The node starts one
   dispatcher for each served project whose config enables it (decision 9).
   A project that enables nothing gets exactly the node it has today, and the
   CLI never runs the dispatch loop. What kobzar planned to show (the queue,
   running sessions, blocked questions, budgets) becomes part of the node's
   web UI, and the kobzar repository is retired.

2. **The dispatcher never writes in a person's checkout.** It writes only in
   worktrees it creates and owns, under a state directory the node owns: one
   per open work branch and one for merging into main. A worktree it created is
   clean by construction, so a dirty checkout elsewhere is never its concern.
   If one of its own worktrees is dirty when it comes back to it, after a crash
   for example, it stops work on that document and escalates it instead of
   committing stray changes. Inside its worktrees it may write any file: the
   inventory through the engine's command cores, and an agent's code as
   ordinary files. The node's existing edits in a served checkout stay as they
   are, written and never committed.

3. **Every dispatcher write is a commit, and every commit is pushed.** A
   commit is what makes a stage visible to `next` and to the node's ref reader
   ([ADR-0070 — Declared work branches carry a document through its stages; main stays the truth for completion](ADR-0070.md)), and a push is what makes it visible to other machines. Commits
   carry one configured identity, and the dispatcher refuses to commit as
   anyone else.

4. **A claim is a git push.** To take an item, the dispatcher makes one
   `apply` batch in the item's worktree (the stage, the `claim_field` value
   and a log entry), commits it, and pushes the work ref fast-forward-only.
   For an item still at its starting status on main, that push creates the
   ref. A rejected push means another dispatcher won: the local commit is
   dropped and no run starts. The claim value names the dispatcher instance
   and the run. A release is the same kind of push, so a holder that pushed
   in the meantime keeps its claim.

5. **Agents run outside opys and never touch the tracker.** The dispatcher
   starts each run through a configured runtime command (a sandbox per run
   today; the ACP runtime kobzar planned, later), handing it the worktree's
   content, the stage's prompt and the role's model. A run returns files and
   a small result: an outcome, a summary, and the stage to resume at. The
   dispatcher decides which files to accept, writes the document through the
   engine, commits and pushes. An agent never pushes and never writes an
   inventory document.

6. **Routing is the config opys already has.** The dispatcher runs only the
   roles that have a `[dispatch.roles.<name>]` entry, and offers a role only
   the documents `next --status S --role R` returns for it. Owners, ranking,
   blockers, orphans and claims stay the engine's ([ADR-0068 — Statuses are owned by declared roles; a role is only a name](ADR-0068.md), [FEAT-0057 — `opys next`: the pick oracle](FEAT-0057.md)), and
   role kinds stay descriptive ([ADR-0072 — Role kinds describe workers and choose the initial queue](ADR-0072.md)). Stage order is declared; by
   default a status later in the type's `statuses` list is served first, so
   work in flight finishes before new work starts. Whether an item is ready is
   said in the inventory, by blockers and required links that `next` already
   evaluates. Where those are not enough, opys gains the predicate; the
   dispatcher does not grow its own.

7. **The dispatcher acts where `verify` only observes.** Liveness is the
   dispatcher's own session state, never a copy's `updated` time. A claim it
   holds with no live session is released as soon as it notices; a claim held
   by anyone else is released only after `claim_ttl`. A failed run is retried
   a bounded number of times and then goes to the project's human stage. So
   does an item sent back too many times, with `max_visits` as the backstop.
   `verify` keeps reporting all of these, and `verify --fix` still never
   releases a claim or merges.

8. **Merging stays git's, and only the dispatcher merges.** At a human stage
   a person approves, rejects with a note, or answers and names the stage to
   resume at, from the node's role page or a CLI command that asks the node.
   Approval is a dispatcher control rather than a status edit, because what
   follows it is a merge. On approval the dispatcher merges the work branch
   into main in its merge worktree, sets the branch's declared `merged`
   status, folds or drops scaffolding as the project configures, and pushes
   main fast-forward-only together with the ref's deletion. Landing an
   implementation is the same merge preceded by the project's gate command;
   the dispatcher runs it for the landing stage's owner, an automation role,
   so nothing waits at landing for a person. A rejected push means main
   moved: the dispatcher merges and gates again. A merge conflict goes to the
   human stage, because opys never resolves divergence itself ([ADR-0027 — Files and git are the only truth; the server is a view](ADR-0027.md)). A
   pull request the dispatcher watches is an alternative approval style per
   type.

9. **Config is split by who owns the setting.** `opys.toml`, versioned with
   the project, gains `[dispatch]` for what the project decides: which roles
   are dispatched with which runtime and model, the prompt for each stage,
   stage order, the approval style per type, how scaffolding is handled, and
   the gate command. Prompts are committed files read from main, so a branch
   cannot change its own instructions. The node's config, beside the
   allowlist, holds what the machine decides: whether this node dispatches at
   all, worker counts per role, quota sources and thresholds, the commit
   identity and signing key, forge credentials and where notifications go.
   Credentials never enter a repository.

10. **What only the dispatcher knows stays out of the inventory.** Sessions,
    the run ledger, run logs and quota snapshots live in the node's state
    directory. The web UI shows them, with controls to pause dispatch and to
    retry, release or stop a run. Nothing in the engine reads them, so they
    never become a second source of truth ([ADR-0027 — Files and git are the only truth; the server is a view](ADR-0027.md)). What a run decided is
    written into its document as a log entry, so the history that matters
    stays in git.

## Consequences

- The README's "Orchestration is not opys' job" becomes "opys ships an opt-in
  dispatcher, and the engine and CLI still start no write off their own
  clock". On acceptance, the README and the orchestrator mentions in the skill
  and format.md change with it. [FEAT-0057 — `opys next`: the pick oracle](FEAT-0057.md)'s scope, [ADR-0053 — Branches are progress, main is truth](ADR-0053.md)'s scope note,
  [ADR-0068 — Statuses are owned by declared roles; a role is only a name](ADR-0068.md) decision 8 and [ADR-0070 — Declared work branches carry a document through its stages; main stays the truth for completion](ADR-0070.md) decisions 4 and 5 then read as naming
  opys's dispatcher where they name a separate orchestrator; none of what
  they leave out moves into the engine. [ADR-0027 — Files and git are the only truth; the server is a view](ADR-0027.md) is extended, not changed:
  files and git remain the only truth, and git remains the only merger.
- [ADR-0053 — Branches are progress, main is truth](ADR-0053.md)'s two orchestrators that double-pick until one fetches become two
  nodes whose second claim push is rejected. Freshness still depends on
  fetching, so the dispatcher fetches before it picks.
- The node becomes a process that spends money and merges to main. It still
  has no authentication and still binds to loopback by default, and that stays
  the boundary: a node that dispatches is not exposed beyond its machine until
  authentication is decided separately.
- opys takes on code it never owned: worktrees, pushes, merges, quota checks,
  notifications and a forge client. The runtime, the quota source and the
  notifier are commands named in config, and a forge is one adapter, so none
  of their dependencies reach the engine.
- The dispatcher spawns `git` for worktrees, merges and pushes. [ADR-0053 — Branches are progress, main is truth](ADR-0053.md)'s
  "gix, never a spawned git" keeps covering the engine's reader, which stays
  in-process. Like work branches, `[dispatch]` is refused at config load in a
  build without the `git` feature.
- The new crate joins the workspace under the shared version and the 1.88
  MSRV, and is Apache-2.0 like every crate here ([ADR-0033 — Apache-2.0, permanently, for every crate in this workspace](ADR-0033.md)).
- The existing dispatchers can move over one setting at a time, because the
  opys config they rely on (roles, owners, work branches, claim fields) does
  not change.

## Open questions

- Should the node commit a person's own web UI edits? Today's dispatchers push
  them on every tick; this decision leaves them uncommitted.
- What is the runtime command's contract (its inputs and its result), and how
  is it versioned?
- Should the dispatcher also run without the node, in the foreground, for CI
  or a one-off run?
- Git worktrees, or jj workspaces where the repository is colocated?

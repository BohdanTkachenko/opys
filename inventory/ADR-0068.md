# Statuses are owned by declared roles; a role is only a name

## Context

The loop opys serves now has more than one kind of worker. One project already
runs its whole pipeline as status queues: an agent per waiting status takes the
next item with `opys next --status`, claims it, does its step and hands it on.
Two of those queues, `spec-approval` and `needs-human`, are worked by the
person who owns the project, and every item in them is something that person
has to do. Three questions follow, and opys answers none of them today:

- **What is waiting on me?** A person wants this across every project the node
  serves. An agent wants it within one project.
- **Who works this status?** That project keeps the answer outside opys, in its
  runner's own config, so the inventory cannot say that `spec-approval` is a
  person's queue. [FEAT-0060 — Flow graph view: statuses as nodes, documents on them](FEAT-0060.md) wanted to draw such a status as a gate with a
  `human = true` flag. It never shipped, because there was nowhere to declare
  the flag.
- **Who is a comment for?** [ADR-0062 — Comment threads live in the document they discuss](ADR-0062.md) derives a thread's turn from the kind of
  its last author, `human` or `agent`, so it assumes two parties. A project
  with two agents and a person has three.

No project can be expected to name a status `needs-human`. One project marks
documents waiting for review with an `unreviewed` tag; another might call its
gate `approval`, `sign-off` or `review`. So the answer to "what is waiting on
me" has to come from config the project writes, not from guessing at names.

The founding stance, "no sprints or assignees", is the other constraint.
[ADR-0046 — Priority is an opt-in declared field the board orders by](ADR-0046.md) admitted priority as an opt-in declared field without turning opys
into a project-management tool. The same boundary applies here.

The options:

1. **A per-status flag** (`human = true`). It answers "does a person work
   this" and nothing else. An agent still needs the runner's map to find its
   queue, two people cannot be told apart, and the engine gains a kind it has
   to treat specially.
2. **Roles with a kind** (`kind = "human" | "agent"`). Nothing in opys would
   behave differently by kind: `next`, `verify` and every view work the same
   for both. The kind would be stored and never read, and it invites the
   special cases of option 1.
3. **Per-document assignees.** Every transition would have to name the next
   worker, the queue that a status already *is* would be lost, and these are
   the task-board semantics the founding stance rules out.
4. **Inference**: from status names, from which statuses no runner picks,
   from who committed the moves out of a status, or from a model's guess. None
   of it is deterministic or derived from the files ([ADR-0027 — Files and git are the only truth; the server is a view](ADR-0027.md)), so neither a
   page nor a dispatcher could trust it. At most it could suggest config, and
   the node's discovery shows that suggesting is a separate job.
5. **Declared roles, as plain names, that own statuses.** Chosen.

## Decision

1. **A role is a declared name, and nothing more.** It is declared as
   `[roles.<name>]` in `opys.toml`, with an optional `description`, and the
   name matches `^[a-z][a-z0-9-]*$`. A role has no kind and no flag. `human`
   is a convention a project may follow, not a keyword: nothing in the engine,
   the node or the web UI compares a role to a literal name. A project can
   declare `human`, `dan`, `agent-claude`, `agent-codex`, `upstream` or
   `legal`, and all of them behave the same.

   ```toml
   escalate_to = "human"

   [roles.human]
   description = "Dan: sign-offs and decisions"

   [roles.agent-claude]
   [roles.agent-codex]
   ```

2. **Roles own a type's statuses.** `[types.X.owners]` maps a status to one
   role or to a list of roles:

   ```toml
   [types.task.owners]
   todo          = "agent-claude"
   spec-approval = "human"
   ready         = ["agent-codex", "agent-claude"]
   needs-human   = "human"
   landed        = []          # waits on no one
   ```

   A list means any of its roles may take the item. The order is a hint for an
   orchestrator; opys ranks nothing by it.

   The map is opt-in. A type without it is unowned and behaves byte for byte
   as before.

   Once declared, the map is the whole truth, like `transitions`. Every
   non-terminal status of the type must be a key, so a forgotten status is a
   config problem rather than a queue nobody reads, and `[]` says on purpose
   "settled, waits on no one". `config validate` reports each of these as a
   problem:
   - a key that is not one of the type's statuses;
   - a terminal status as a key (nothing waits at one, because `close` deletes
     an ephemeral document);
   - a role that is not declared.

3. **A document may override its owners for the status it is at.** A type that
   declares a field named `owner` with the new field type `role` lets a
   document name the role it waits on, instead of its status's owners. Two
   uses: a review that must go to the other model family, and a `needs-human`
   item routed to an agent to research first.

   Any move to a different status clears the override, unless the same
   `opys apply` sets it again. So an override never outlives the step it was
   written for and never becomes a standing assignee.

   `type = "role"` works on any field, and `verify` requires its value to be
   a declared role. Only the field named `owner` carries the override. On a
   type that declares `owners`, a field named `owner` must have type `role`.

4. **"Waiting on a role" is derived, never stored.** A document waits on role
   R when R is among its effective owners: the override if there is one, else
   its status's owners. One engine module is the only reader of `[roles]`,
   `owners`, the override and `escalate_to`, the way `lifecycle` is the only
   reader of `transitions`. `next`, the new `queue`, the flow view, the
   document view and the node's role page all ask that module.

5. **What the automation could not handle goes to a declared role.**
   `escalate_to`, a top-level key, names the role that receives the documents
   opys can see need a person or a fixer:
   - orphaned ones, with `next`'s reason;
   - ones with time observations, stuck or overflowed ([ADR-0052 — Verify observes time: stuck, visits, `--fix`, and exit code 3](ADR-0052.md));
   - ones with `verify` findings.

   They appear on that role's queue under **attention**, each with its
   reasons. They also stay wherever their status puts them. Without
   `escalate_to`, these documents are reported only where they are today.
   Apart from this pointer, the role has no special standing.

6. **Comment threads are addressed to roles.** This amends [ADR-0062 — Comment threads live in the document they discuss](ADR-0062.md) decisions 3
   and 6 while that ADR is still proposed. In a project that declares roles:
   - An entry records its author's role and the role it is addressed to:
     `- **name** · agent-codex → human · <timestamp>`.
   - A thread waits on the role its last entry addresses. That is still
     derived from the entries, so it cannot drift from them.
   - `--turn=agent|human` becomes `--waiting-on <role>`.
   - By default a reply is addressed to the role of the last entry's author.
     When the replier wrote that entry too, the reply goes to the role that
     entry addressed.
   - A new thread is addressed by default to the document's owner, when the
     document has exactly one effective owner and it is not the author's role.
     Otherwise the author must name the role.

   A project with no `[roles]` keeps [ADR-0062 — Comment threads live in the document they discuss](ADR-0062.md)'s two kinds and its derived turn
   unchanged.

7. **How to ask.**
   - `opys queue <role>` lists everything waiting on a role in one project.
     Each owned status is a group with `next`'s split into pickable, blocked
     and orphaned items. Attention follows, and threads once comments exist.
     The output has a stable payload, `opys.queue/1`.
   - `opys next --status S --role R` narrows the pick oracle to documents R
     owns.
   - `OPYS_ROLE` names the caller's role, so an agent harness sets it once and
     runs `opys queue`.
   - The node serves the same payload per project, and merges it **by role
     name** across every project it serves into a role page. A person opens
     that page, picks a role and sees their items. Names must match exactly: a
     project that calls the person `dan` has a different role until that role
     is renamed.

8. **What stays out of opys:**
   - which agent, model or prompt works a role (the runner decides);
   - claims, leases and liveness ([FEAT-0057 — `opys next`: the pick oracle](FEAT-0057.md)'s orchestrator);
   - notifications (anyone can poll `queue --json`);
   - identity: the node does not authenticate a role choice. Whoever can open
     the node can open any role's page, just as they can open any document
     today ([ADR-0031 — The node serves an explicit allowlist; discovery only suggests](ADR-0031.md)).

## Consequences

- The founding line becomes "no sprints; ownership only as opt-in config on
  statuses", in the README, the skill, format.md and the agent instructions.
  The boundary that matters survives: a project that declares nothing has
  exactly the tool it had, and no document carries a standing assignee.
- This supersedes [FEAT-0060 — Flow graph view: statuses as nodes, documents on them](FEAT-0060.md)'s unshipped `human = true` gate: a flow node shows
  its owners, whatever they are called.
- A project's lifecycle config now names its workers. Moving a status from one
  agent to another is an `opys.toml` edit, and so is renaming a role so two
  projects share one page. That is accepted: the map changes far less often
  than documents do, and git shows every change.
- A runner that keeps its own status-to-worker map can read owners from
  `opys.toml` instead, and keep only prompts, models and outcomes.
- `config validate` gains the owner checks, and a project that adopts `owners`
  must cover every non-terminal status at once. That is the point: a status
  nobody owns is a queue nobody reads.
- `opys.next/1` gains fields (the `role` echo and each item's `owners`). They
  are omitted when empty, so a project without roles gets byte-identical
  output. `opys.queue/1` is a new compatibility surface.
- Every path that changes status clears `owner`: `set-status`, `apply`,
  `verify --fix` and the node's typed actions. An implementer has to keep one
  rule: when `apply` is given an `owner`, it writes it back after the
  transition clears it.

# Work branches: a document's stages on its own branch

A task leaves the pool on main and gets its own branch, `spec/TASK-0420`.
Agents plan, research, condense, write and review on that branch, one status
per stage, and each picks its next item with `opys next --status research` as
it always did: opys answers from the branch. When the spec is finished the
branch sits at `spec-approval`, owned by a person, who sees it in
`opys queue` and on the node. After approval the orchestrator merges it and
main says `ready`; the implementation then runs the same way on
`impl/TASK-0420`. The decisions are in [ADR-0070 — Declared work branches carry a document through its stages; main stays the truth for completion](ADR-0070.md).

## Scope

**In scope:**
- config: `[types.X.work_branches.<name>]` with `ref`, `from`, `stages`,
  `merged`; `claim_field` and `claim_ttl` on the type; refused without the
  `git` feature;
- the engine: a document's effective copy (its work branch's copy inside a
  declared stage, main's otherwise), built on `git::occupancy`;
- `next`, `queue`, `list --status`, `show` (which copy, from which ref) and
  their JSON payloads; the main copy reported as occupied;
- claims: `next` leaves claimed copies out; `queue` and the node show holder
  and age; `verify` reports a claim past its ttl;
- `verify` checks from [ADR-0070 — Declared work branches carry a document through its stages; main stays the truth for completion](ADR-0070.md) decision 6;
- the node: flow and role pages place a branch-held document at its stage,
  with the ref and claim; edits to it go to the branch copy where the branch
  is checked out, and are refused with a reason where it is not;
- documentation: the config reference, the format reference and the README.

**Out of scope:**
- Creating, pushing, merging or deleting branches, and anything about pull
  requests or forges: the orchestrator's ([ADR-0027 — Files and git are the only truth; the server is a view](ADR-0027.md)).
- Folding scaffolding (a brief, a fact sheet) into the finished document: the
  orchestrator's, at merge time.
- Fetching remotes.

## Test plan
- [ ] a document at its starting status on main and at `research` on its declared work branch is picked by `next --status research`, not by `next --status todo`
- [ ] a branch that is not declared, holding the same document at `research`, does not make it pickable (progress only)
- [ ] a claimed branch copy is left out of `next` and shown with holder and age by `queue`
- [ ] `verify` reports two work branches of one kind, an undeclared stage on a branch, main drifting while a branch is open, and a claim past its ttl
- [ ] after the branch merges, main's copy at the declared merged status is the only copy, and history shows every stage
- [ ] a type without declarations, and a project without git, behave exactly as before; a declaration in a build without `git` is refused at config load
- [ ] `queue` for the person owning `spec-approval` lists a branch-held document with its ref

## Manual verification

### Setup
- A project whose task type declares `spec/{id}` work branches with the stages above.
- A task at `todo` on main, and a branch `spec/<id>` where it is at `spec-approval`.

### Procedure
1. Run `opys next --status todo` and `opys next --status spec-approval`.
2. Run `opys queue <the person's role>`.
3. Open the node's flow and role pages.

### Expectations
- `next --status todo` leaves the task out and names it as occupied by `spec/<id>`.
- The task appears at `spec-approval` in the queue and on both pages, labelled with its branch.

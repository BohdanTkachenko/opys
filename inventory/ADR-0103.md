# Interleaved id sequences replace lease blocks

## Context

[ADR-0055 — ID allocation: local lock, lease blocks in a ref, renumber as repair](ADR-0055.md) layered id allocation three ways: the advisory lock for one machine,
lease blocks in an orphan git ref for cross-branch work, and `renumber` as the
repair of last resort. The middle layer ([FEAT-0081 — ID lease blocks in an orphan git ref](FEAT-0081.md)) was never built, and its own
feature text spends half its length on what makes it hard: a non-standard ref
outside the default fetch refspec, so a fresh clone allocates from an empty
ledger; branch-protection carve-outs nobody has documented; a commit-and-push
round trip as the compare-and-swap.

Agent loops ([FEAT-0109 — Flow graph view: statuses as nodes, agents as loops](FEAT-0109.md)) change the frequency of the problem. Creating documents
on branches stops being occasional: a coder that finds a bug files it there and
then, on its branch, because main did not anticipate it, and restraining
creation to main would take that away. So every branch allocates, collisions
become routine, and a `renumber` at merge changes a handle that is already in
commit messages and Progress logs.

The invariant is monotonicity and never-reuse, not density; [ADR-0055 — ID allocation: local lock, lease blocks in a ref, renumber as repair](ADR-0055.md) already
accepts gaps.

## Decision

Ids are allocated from **interleaved sequences**. A project sets `[ids] modulus
= M`. Each allocator has a *slot* `k` in `0..M`: from `OPYS_ID_SLOT` when set
(an orchestrator sets one per agent it spawns), otherwise a stable hash of user
and host modulo `M`. `new` allocates the smallest number congruent to `k` modulo
`M` that is greater than every number it has ever seen, in live documents, the
retired ledger and every relation map. Two allocators with different slots
cannot collide, on any branches, with no push, no ledger and no ref. Two with
the same slot are a misconfiguration, and `renumber` repairs that exactly as it
repairs today's collisions.

With no `modulus` configured, allocation is today's dense sequence,
byte-identically. A project adopts interleaving when it goes multi-branch. The
seam is the existing `ids::IdSource`: an `Interleaved { slot, modulus }` source
beside `SequenceMax`, constructed behind `Ctx` (the move [FEAT-0081 — ID lease blocks in an orphan git ref](FEAT-0081.md) said had to
happen first still happens).

## Consequences

- [ADR-0055 — ID allocation: local lock, lease blocks in a ref, renumber as repair](ADR-0055.md) is superseded on its second layer only; the lock and `renumber`
  stand. [FEAT-0081 — ID lease blocks in an orphan git ref](FEAT-0081.md) goes to `wontfix` with this decision as the reason, on
  acceptance ([TASK-0122 — engine: interleaved id sequences](TASK-0122.md)).
- Gaps of `M - 1` between one allocator's consecutive ids. At `M = 16` and
  `pad = 4`, four digits hold roughly six hundred documents per slot; the
  padding guidance in format.md says so.
- `verify` is unchanged: `check_unique_numbers` and the never-reuse ledger are
  exactly the invariants interleaving preserves.
- A solo user on one machine sees no difference until they set a modulus.
- Prior art: multi-master auto-increment offsets in replicated databases.

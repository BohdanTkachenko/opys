# The node serves an explicit allowlist; discovery only suggests

## Context

[FEAT-0058 — opys-server: the always-on node](FEAT-0058.md) spec'd the node as `opys-server run <roots…>`: roots on argv, walked
recursively, and every `opys.toml` found underneath becomes a served corpus.
Two things are wrong with that.

**Consent.** The served set is a side effect of where you pointed the process.
Everything under the root — private client work, a throwaway clone, someone
else's checkout — becomes readable *and writable* over HTTP/WS the moment it
acquires an `opys.toml`. This same list is what the relay ([FEAT-0059 — Relay and Connect: remote access to your nodes](FEAT-0059.md)) later
exposes beyond the machine, and a scan result is the wrong thing to expose.

**Cost.** Measured on the maintainer's workstation with the walk the server will
actually use — `walkdir`, hash-set skip list, warm dentry cache — over a `$HOME`
holding 6.4M filesystem entries, 3.3M of them under `~/Projects`. Time to find
every `opys.toml`:

| skip list | depth 4 | depth 6 | depth 8 | depth 10 | unbounded |
| --- | --- | --- | --- | --- | --- |
| hidden + `target` + `node_modules` | 11 ms | 130 ms | 375 ms | 713 ms | 1326 ms |
| the wider build/vendor/cache list | 10 ms | 124 ms | 318 ms | 495 ms | 681 ms |

Every variant finds the same six projects, each one directory below
`~/Projects`. Two things fall out. Cost climbs steeply with depth — roughly
double per two levels — so an unbounded walk is the one shape worth refusing.
And a wider skip list nearly halves the deep scans, pruning ~1.3M entries
dominated by `third_party` (824k), `target` (412k), `node_modules` (229k) and
`out` (169k). An earlier `find`-based measurement suggested pruning bought no
time at all; that was an artifact of `find` evaluating chained `-name` tests
against every entry, and it does not carry over to a hash-set membership check.

Cold-cache figures were not measured (dropping caches needs root) and are
materially worse — an argument for doing this off the critical path rather than
for doing less of it.

Argv roots also bake the served set into the systemd unit's `ExecStart`
([TASK-0075 — opys-server: systemd install, docs, and M1 closeout](TASK-0075.md)), so adding a project meant editing a unit file and reloading the
daemon.

## Decision

The node serves a persistent **allowlist**, never a scan result. The registry
lives at `~/.config/opys/server.toml` (XDG) and holds two kinds of entry: an
explicit project (a directory containing `opys.toml`) and a prefix (every
project under a directory, with its own depth bound). Nothing outside a matching
entry is ever served.

Discovery is demoted to a **suggestion** service: an on-demand scan that
proposes "found these projects" for approval, offered in the web UI and as
`opys web scan`. It never registers anything by itself.

Suggestion scanning runs as a **background job** — never on a request path, never
blocking startup. It walks up to 10 levels below each scan root (default root
`~`), skipping hidden directories and a named list of build, vendor, and cache
directories: `node_modules`, `target`, `build`, `dist`, `out`, `vendor`,
`third_party`, `__pycache__`, `venv`, `Pods`, `DerivedData`, and the Unreal trio
`Binaries`/`Intermediate`/`Saved`. That combination measures ~0.5 s on the
workstation above: deep enough that no plausible project layout is missed, cheap
enough to be invisible when nothing is waiting on it. The skip list earns its
keep twice, since it also stops an `opys.toml` vendored inside `node_modules`
from ever being suggested.

Serving and suggesting are separate loops because their costs differ by three
orders of magnitude. **Serving** re-checks only what is already known — stat each
served project and its `opys.toml` — which is O(served projects) and can run on a
short timer. **Finding** anything new, whether a fresh project under a prefix
entry or a suggestion outside the allowlist, rides the background scan: startup,
on demand, and a slow timer (hourly), never a 60-second one, because half a
second of walking every minute forever is a real cost for a result that changes
weekly. A project created under a prefix entry is exactly as rare as one worth
suggesting, so both wait for the same pass and one depth bound governs both.

The CLI surface moves under the `opys` binary, which [ADR-0076 — Apache for what runs on your machine; copyleft for the scaling layer](ADR-0076.md) makes possible:
`opys web start`, `opys web add <path>`, `opys web remove <path>`, `opys web
list`, `opys web scan`, `opys web install`. `add`/`remove` edit the config file
and nothing else — they never speak to a running node, so no endpoint accepts a
filesystem path and [ADR-0052 — The hosted plane is blind and unprivileged](ADR-0052.md)'s typed-action guarantee stands unchanged. A
running node watches its registry file and picks up edits on the next debounce,
with the periodic rescan as backstop.

Git worktrees are still found through `git worktree list` per allowlisted
project — a targeted call, not a deeper walk — so the depth bound costs no
worktree coverage.

## Consequences

- `opys-server run <roots…>` as shipped by TASK-0067 is gone: `run` takes no
  roots. TASK-0067 is closed, so [TASK-0069 — opys-server: project discovery and the corpus registry](TASK-0069.md) carries the amendment along with the
  registry itself.
- [TASK-0069 — opys-server: project discovery and the corpus registry](TASK-0069.md) changes from "turn argv roots into corpora" into the registry, the
  allowlist matcher, and the bounded background scan. [TASK-0075 — opys-server: systemd install, docs, and M1 closeout](TASK-0075.md)'s systemd unit
  becomes static (`ExecStart=… web start`), making service installation a
  one-time step independent of which projects are served.
- [TASK-0070 — opys-server: corpus actor with warm store and watcher](TASK-0070.md)'s "re-run discovery every 60 s" splits in two: the cheap
  allowlist re-check keeps that cadence, and the deep suggestion scan moves to
  the background job's slow timer.
- The relay inherits a list the user explicitly approved — the right unit both
  to expose remotely and to render in a "what am I sharing" view.
- A fresh install serves nothing until something is added. That friction is the
  point; `opys web scan`'s suggestions and `opys web add .` keep it to one step.
- The CLI links the node's dependency stack (axum, tokio, hyper, notify). A
  release build of the node binary is 2.4 MB against the CLI's 18.4 MB, so the
  cost is low single-digit megabytes on a binary that already carries GlueSQL
  and a markdown renderer. Linked unconditionally rather than behind a cargo
  feature: a `cargo install opys` whose `opys web` fails to exist would defeat
  the reason for folding it in.

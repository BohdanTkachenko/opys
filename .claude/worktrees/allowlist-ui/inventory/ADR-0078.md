# Svelte for the web UI; built assets are committed and drift-checked

## Context

[FEAT-0058 — opys-server: the always-on node](FEAT-0058.md) settled the UI stack as "no build pipeline — vanilla ES modules and
one stylesheet, embedded via `include_str!`". That was the right call for a
dashboard. [TASK-0074 — opys-server: embedded web UI](TASK-0074.md) is not a dashboard: it is a sidebar of project groups, a
board with type/tag/text filters, a document view with an action bar posting to
the write endpoint, a query console, a worktree union table, and live refresh
driven by a WebSocket that has to re-render whichever view is active and
reconnect with backoff. Six views with real state.

This is also the only human surface the product has. The TUI was retired in
[ADR-0050 — Retire the TUI; the web UI over the server is the human surface](ADR-0050.md) in its favour, and a live dashboard is what the project leads with. Hand-rolled DOM code is cheapest at the start and most
expensive exactly where this UI is going.

The constraint that shapes the *how* is packaging. `cargo install opys` must
work with no Node toolchain, and two build environments that matter here have no
network at all: the nix flake's `rustPlatform.buildRustPackage` sandbox, and
docs.rs, whose policy is that network access is never enabled for any crate.
Anything that fetches at build time fails in both.

How other projects solve this splits three ways:

- **Commit the built assets.** The build runs in the developer's shell or CI,
  the output is checked in, and the crate embeds it with `include_str!` or
  `rust-embed`. Consumers need nothing. This is the common answer for crates
  that must publish to crates.io.
- **Download at build time.** Meilisearch's mini-dashboard does this: package
  metadata names an `assets-url` pointing at a GitHub release, and `build.rs`
  fetches and unpacks it. It works, which is why it is worth naming — but it is
  behind a cargo feature precisely because every consumer without network at
  build time fails, and it introduces version skew between the crate and the
  asset release plus a hash-pinning problem for fetched executable code.
- **Sidestep `cargo install`.** Ship prebuilt binaries from GitHub releases
  (cargo-binstall and friends) and treat building from source as the fallback.
  Orthogonal: the fallback still has to work.

## Decision

The web UI is written in **Svelte 5** — Svelte and Vite producing a static
bundle, not SvelteKit, which brings routing, SSR and adapters this does not
want. Sources live in `opys-server/ui/`, the client-side hash routing and view
list of [TASK-0074 — opys-server: embedded web UI](TASK-0074.md) are unchanged, and **zero external requests remains a hard
rule**: no CDN, no webfonts, everything in the bundle, the page works offline.

**The built output is committed** to `opys-server/ui/dist/` and embedded with
`include_str!`/`include_bytes!` exactly as the current plan does. The crate
build never runs Node, so `cargo install opys`, `cargo build` from a git
checkout, docs.rs, and the nix package all keep working untouched and offline.

A CI job rebuilds the bundle and fails if it differs from what is committed.
This repo already has that gate in the form of `scripts/sync-versions.sh
--check`; the UI gets the same shape, so committed output can never drift from
its sources. Node lives in the flake devShell only, alongside a `ui-build`
command, and is never a dependency of the crate build.

Build-time downloading is **rejected**. It breaks the flake package and docs.rs
outright, and buying that back would mean a feature flag that leaves the default
build without a UI — which for a product whose only human surface is this UI is
worse than a directory of generated files.

## Consequences

- Generated files enter the tree, which cuts against this repo's
  no-generated-artifacts grain (no `INDEX.md`, everything derived live). Bounded:
  one directory, marked `linguist-generated` in `.gitattributes` so reviews are
  not flooded, and provably in step because CI rebuilds it.
- A UI change is now two steps — build, then commit both sides. Forgetting the
  first turns the pipeline red rather than shipping a stale bundle.
- A second dependency ecosystem arrives: `package-lock.json`, a pinned Node
  version, and npm advisories to watch. It touches the devShell and CI only, so
  the MSRV floor and the crate's dependency tree are unaffected.
- The bundle's size becomes a number worth watching, since it ships inside every
  `opys-server` binary. Svelte compiles most of its runtime away, so the target
  is tens of kilobytes; a regression here is a review comment, not a crisis.
- [TASK-0074 — opys-server: embedded web UI](TASK-0074.md)'s spec is rewritten around this, and [FEAT-0058 — opys-server: the always-on node](FEAT-0058.md)'s "Web UI stack"
  decision is replaced by it.
- Preact plus htm — vendored ES modules, components and reactivity with no build
  step at all — was the considered alternative and would have preserved the
  original decision intact. It was passed over for editor support, type
  checking, and component ergonomics across six views. If the pipeline ever
  proves more trouble than it saves, that is the fallback, and the API contract
  the UI consumes makes swapping front ends a local change.

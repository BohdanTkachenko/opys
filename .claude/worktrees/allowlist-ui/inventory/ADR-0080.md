# Apache-2.0, permanently, for every crate in this workspace

## Context

Earlier licensing decisions in this project recorded a *current* scope — which
crates were Apache-2.0 as of the day they were written — and left room to
revisit. That was appropriate while the shape of the product was still moving.
It is not what the project now wants to say.

opys asks people to build on it: to put the inventory that describes their
product into a format this tool defines, to wire `verify` into their CI, and to
let agents write to it unattended. That is a large amount of trust to ask for a
tool whose licence is described as current rather than permanent. A project that
relicenses after acquiring users spends credibility it does not re-earn, and
enough projects have done it recently that readers now look for the clause
rather than assume it. A promise made only in a launch post is not a promise;
it is marketing. This is the decision of record behind it.

## Decision

Every crate in this workspace is **Apache-2.0, permanently**: `opys-engine`,
`opys-backend-markdown-local`, `opys` (the CLI), and `opys-server` (the
always-on node, including its embedded web UI). All four publish to crates.io
together under that licence.

The promise names crates rather than drawing a boundary around a category like
"what runs on your machine", because a category has an edge and an edge invites
argument about which side a new component falls on. A list does not. Anything
added to this workspace joins the list, or it does not belong in this workspace.

Nothing is withheld from the open-source build. There is no feature gate, no
"community edition", and no capability that exists in a build someone else can
make but not in the one you can build from this repository.

## Consequences

- The licence stops being a thing to check and becomes a thing to rely on. That
  is the entire point, and it is worth more than the optionality it costs.
- This forecloses a licence change as a business lever for these four crates.
  Deliberately: a lever nobody believes you will not pull is not a lever, and
  one you might pull is a reason not to adopt.
- Outside contributions are now unambiguous. A contributor's work is Apache-2.0
  on arrival and stays that way, so no CLA is needed to keep the option of
  relicensing open — there is no such option to keep.
- Anyone may take this code and run it, modify it, or offer it to others. That
  is what the licence has always allowed; saying "permanently" only removes the
  suggestion that it might one day stop being true.
- A future component that genuinely should not be Apache-2.0 does not get an
  exception inside this workspace. It lives somewhere else, with its own licence
  and its own decision record, and this workspace stays a thing that can be
  described in one sentence.

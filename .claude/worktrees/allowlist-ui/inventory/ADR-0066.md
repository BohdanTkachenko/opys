# SQL is the internal working representation; markdown stays the truth

Recorded retroactively (the work shipped in v0.11.0, `--write` after it),
distilled from the PRD written at the time. [ADR-0051 — Files and git are the only truth; the server is a view](ADR-0051.md) generalizes this
decision to the server; this is where the principle started.

## Context

opys originally loaded every markdown file into a `Vec<Doc>`, mutated the
structs in Rust, and wrote them back. That bespoke model had four problems:

1. **Reads were limited.** `list` offers `--type/--tag/--status/--field`;
   anything relational — joins across the relation graph, cross-tabs, "features
   tagged `area:parsing`, still `planned`, with an uncovered test case" —
   required piping into `grep`/`awk` or a throwaway script. The `[[stats]]`
   feature had already proven SQL was the right tool for corpus aggregation.
2. **The data model was reinvented.** Filtering, id-sequence allocation,
   reference reconciliation, and duplicate detection were each hand-written
   over `Vec<Doc>` — all of them declarative one-liners in a relational engine.
3. **No bulk-edit story.** "Mark every bug tagged `abc` as done", "rename a tag
   value corpus-wide" meant scripting many CLI invocations. Users (and agents)
   kept reaching for SQL-shaped thinking; opys had no answer.
4. **Fidelity risk was unquantified.** Any "SQL over markdown" scheme hinges on
   a lossless markdown⇄structure round-trip. That had to be *proven* before
   anything could be built on it.

## Decision

Per CLI invocation: **load markdown → decompose into an in-memory GlueSQL
database → run SQL (plus Rust for the invariants) → flush changed documents
back to files.** The database is the working representation; the markdown files
remain the sole durable truth. Four rules bound it:

- **Not a database product.** The DB is rebuilt from the files every invocation
  and discarded: no `.db` file, no migrations, no daemon, no schema versioning.
  The single-binary, no-runtime-dependency property is preserved.
- **Fidelity is the gate.** Every frontmatter key has exactly one home;
  arbitrary YAML round-trips through `fm_fields.value_yaml`; derived columns
  are computed in exactly one place, so dual-write divergence is impossible by
  construction. The invariant `reconstruct(decompose(doc)).to_text() ==
  doc.to_text()` is a test, held over adversarial YAML and a real 1,377-doc
  corpus.
- **SQL is the data layer only.** Rules, linkify, mdprism, and section checks
  stay Rust, fed reconstructed `Doc`s. SQL never encodes an invariant.
- **The user-facing surface is additive** ([FEAT-0010 — SQL query surface](FEAT-0010.md)). `opys query` is
  read-only by default — every statement must be a SELECT, checked on the
  *plan* before anything executes, so a `DELETE …; SELECT 1` compound is
  rejected outright. `--write` allows DML against the authoritative tables and
  flushes **only if the edit introduces no new `verify` problem** ("no worse",
  not "must pass", so it stays usable on a corpus with transient issues).
  Because flush is the only thing that writes files, refusal *is* rollback.
  Agents still read with `grep`; nothing about the existing mental model
  changed.

Explicitly **not** decided here: translating DML into lifecycle semantics.
`UPDATE docs SET status='done'` edits a column; it does not become a `close`
(delete + strike references). Raw column edits only — see Consequences.

## Consequences

- **Parity was the acceptance bar and was met**: a differential battery
  (new/set-status/tag/block/unblock/close/retire/import/cleanup/sync) run under
  the pre-rewrite and post-rewrite binaries over identical 1,377-doc corpora
  produced byte-identical inventories; `sync` on an already-synced corpus
  changes zero files. Latency stayed CLI-fast at that scale (list 0.09 s, query
  0.16 s, stats 0.11 s, sync 0.15 s, verify 0.40 s).
- **GlueSQL's limits are load-bearing knowledge.** Internal SQL binds values as
  `$n` parameters (never string interpolation) and uses JOINs only: no `UNION`
  (unsupported), no `IN (subquery)` or FROM-subqueries (executed as O(n×m)
  nested loops), no subquery in `INSERT … VALUES`, and `COALESCE(MAX(…), n)`
  does not rescue an empty-table NULL. Multi-table maxima are combined in Rust.
  Violating these is a silent performance cliff, not an error.
- **Raw DML ≠ lifecycle** is a real sharp edge: the verify gate prevents
  corruption but cannot supply lifecycle side effects. Writing to a derived
  column is a safe no-op that *reports* rows updated, which surprises people.
  Both are mitigated by guarded DML targets and documented writable columns; a
  future DML→command translation layer would remove them.
- **The engine choice is isolated** in the store module, so replacing GlueSQL
  (if its planner or feature gaps bite) is a contained change.
- MSRV is pinned at rustc 1.88 by the dependency tree, reproducible locally
  with the `msrv` devShell command.
- Consequences that later work has already absorbed: the writable `blocks`
  projection extended this model to document bodies; the TUI-on-the-store item
  died with the TUI ([ADR-0050 — Retire the TUI; the web UI over the server is the human surface](ADR-0050.md)); stats still keeps a private throwaway
  projection DB so its `SELECT *` contract stays byte-stable, and unifying it
  with the store's tables remains optional future work.

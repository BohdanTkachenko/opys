# A project's inventory base can escape its root

`base` in `opys.toml` is a path relative to the project root, and nothing checks
that it stays there. `ProjectConfig::validate` never looks at it, and
`Project::open` joins it to the root without normalizing, so `base = "../victim"`
resolves outside the project and every write follows it.

Today this is latent: reaching a project means naming its directory on the
command line, and a user who can do that can already write wherever they please.
It stops being latent the moment something *else* chooses which roots to open —
which is exactly what [FEAT-0083 — Scan modes and first-run onboarding](FEAT-0083.md) proposes. Its containment rules
(`$HOME` only, no dot-components) constrain the directory that gets allowlisted;
they say nothing about where that directory's own config then points. A repo
cloned into the scan root with `base = "../../.ssh"` is allowlisted on its
appearance and writes outside `$HOME` on the first action taken against it.

The severity is bounded and worth stating precisely: this is not silent
exfiltration and not arbitrary *content*. It needs a write action against the
offending project, and what lands is opys' own output — a document, a rewritten
`_retired.md` — in a directory that never consented to it. That is enough to
matter, because the file names and the directory are attacker-chosen.

Containment belongs in the engine, not in the server: `Project::open` is the one
place every consumer already passes through, and a check there covers the CLI,
the node, and anything embedding the library. Canonicalize the resolved base and
require it under the canonicalized root; reject with an `OpysError`, since a
config that points outside its project is a broken config rather than a content
problem `verify` should collect.

## Reproduction

1. `mkdir -p /tmp/esc/proj /tmp/esc/victim`
2. Write `/tmp/esc/proj/opys.toml` with `base = "../victim"` and one document
   type.
3. From `/tmp/esc/proj`, run `opys new --type feature --title escaped`.

It prints `/tmp/esc/proj/./../victim/FEAT-0001.md` and the file lands in
`/tmp/esc/victim/`, outside the project root. Observed on 0.12.0.

## Progress
- 2026-08-29: found while reviewing the containment rules proposed for
  [FEAT-0083 — Scan modes and first-run onboarding](FEAT-0083.md), and verified by running it rather than inferred from the
  source — `base = "../victim"` wrote outside the root on 0.12.0.
- 2026-08-29: fixed. `ProjectConfig::resolve_base` is now the one way to turn a
  config into an inventory path, used by `Project::open` and by the node's
  `discover::corpus`; a lexical check (relative, no `..`, not absolute) plus a
  canonicalized containment check when the directory exists, so a symlinked base
  is caught too. Reported by `validate` as well, so `config validate` names it
  first. Refused as an `OpysError`, exit 2. Full gate green.
